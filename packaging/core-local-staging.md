# Core local engine staging

Build the candidate with `node packaging/build-core-local.mjs --output NEW_DIRECTORY`. The output is a private npm archive and a detached `candidate-manifest.json`. The installed candidate bin accepts `--help` and starts a stdio MCP handshake by default or with `--stdio`. It answers initialization and ping with an empty capability set. The host's local service factory loads the storage slot on demand. Until a real adapter fills that slot, service creation returns `core_local_adapter_unavailable`.

An AST walk from the CLI and each executable core export determines the runtime modules. The walk checks imports and ambient capabilities in the host and core, including unbundled core modules. The storage slot is reachable only through the deferred composition entry, and the CLI can import the stdio entry. The bundled core manifest carries the executable exports with their original names and targets. Candidate modules use relative ESM imports. A future bare dependency, worker entry or asset needs an explicit resolution rule and an inventory check. The source, extracted archive and offline npm installation must agree on the runtime graph and payload file digests. Before publishing the candidate, the builder also runs the installed bin's help and MCP initialize and ping with SQLite disabled and storage loading blocked.

The builder checks `packaging/core-local-files.json` against the candidate-owned runtime modules, the core package manifest and the license. Adding a core runtime module needs no packaging edit.

## Generation identity

`engineIdForCoreLocal` uses `core-local-v1-` followed by the full lowercase SHA-256 of the UTF-8 JSON encoding of `["core-local-v1", sortedPairs]`. Each pair contains a portable archive path and the lowercase SHA-256 of its exact bytes. Sort paths lexically in ASCII order. Include the generated `package.json` and every payload file. The detached manifest records the compressed archive's byte count and hash separately, so repacking the same payload can retain its generation identity. The release verifier should check the trusted manifest, archive and member bytes before using the ID. Keep repair suffixes on published directory names outside the base ID.

## Installer selection and capture activation

Qualify the candidate through an explicit local setup selection while the installed route continues to use the legacy bundle. Before release, wire the qualified host, adapter and default tool set into the candidate. With release approval, bundle its manifest and archive and teach setup to verify the candidate schema, package and bin. Accept both ID formats in descriptor, registration, daemon and capture reference handling so retained generations remain resolvable. Stage and verify the candidate in a fresh generation directory and run its config probe before opening a store. Publish MCP vectors only after the migration and candidate visibility checks pass. Preserve the installed defaults and keep unshipped profiles parked.

Record cutover checkpoints before closing admissions, draining hooks, readers and writers, attesting archival recovery data, committing the migration, and publishing routes. Use an additive new physical version if the compatibility spike passes. Otherwise prepare an attested copy and switch the descriptor after verification. Both paths must prove that the old entry refuses to serve the committed store and that forgotten content stays unavailable. Keep pre-forget backups outside service routing. Initial local parity uses exact matching plus span lineage and hashed fences.

Capture receipts from installer 0.6.11 pin the old engine and Node executable. An MCP registration can publish while those hooks still point at the old generation. Before migration, durably suspend capture through controls the pinned generation enforces and confirm that stale commands and in-flight work cannot reach a writer. For a copied replacement, also keep the old store ineligible for service through its prior route.

After the candidate passes its store checks, use an explicit, journaled activation per enabled client. Preserve the receipt preference, notice and consent, session identity, and source cursor. Verify the new hook command, client approval and current consent before publishing the new receipt and reopening admissions. Leave absent or disabled hooks as configured. When approval is pending or a handoff is interrupted, retain the old references and persist a paused recovery checkpoint. Resume forward from that checkpoint after re-verifying the candidate and client state. Fence stale leases and prevent replay of fenced work before reopening.

Use one SQLite file per installation. Qualify same-file writer serialization across owner scopes and a read snapshot that stays consistent while a writer commits to that file.

Preserve the scoped capture claim key in the migrated ledger. Claim identity includes owner, namespace, client and event ID. Keep claim leases and completed replay scoped to that key, and preserve the session and payload conflict checks. See the [capture conformance case](../packages/conformance/src/capture-cases.mjs#L87) and the [capture port](../packages/core/src/ports/capture.d.ts#L13).
