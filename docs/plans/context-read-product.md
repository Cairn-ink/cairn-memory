# Context-read for the product — P2 contract draft

Status: **revision 3 (`context-read-product-v1.1` draft) for re-check, base `e7dade51`**. This is an explicit pre-implementation version revision of frozen `context-read-product-v1`, not a reinterpretation of that profile. Frozen v1 remains the reference at `e7dade51`; nothing has been implemented. No new freeze, product-adapter sign-off or performance acceptance is claimed. Inventory baseline remains `546d57ac`; P2a coding requires re-check and product sign-off on the revised checklist.

## Changes from v1

- **Authority:** replace the per-owner/per-namespace authority-vector, final-read lease and FIFO revocation protocol with a host-minted request snapshot, two synchronous Worker-local currentness checks and an optional single positive ownerGeneration (§4.1). Stronger synchronized revocation moves to a future Cards/teams package.
- **Guarantee:** publication before entry refuses with authority_required; a change visible at the second check refuses with scope_changed. After that check a request may finish only before its immutable cutoff, never more than 5,000 ms after request admission. There is no promise of atomic revocation/snapshot acquisition. Erasure correctness requires stopped clients and maintenance quiescence.
- **Lifetime/integration:** request credentials are never reused across requests/handles or lent to maintenance. The host resolves async auth/ACL before open, supplies a cheap Worker-local adapter, wires disconnect/error policy/drain, and reauthenticates fallback. Maintenance has independent service authority. The product checklist is replaced with six checks.
- **Version/cache identity:** explicitly select profile `context-read-product-v1.1`; stable data DTO version remains `context-read-v1` and representation-v2 is unchanged. Product sidecar suffix, profile markers and HMAC domains use v1.1 to isolate the changed authority binding. There is no implicit conversion/reinterpretation of frozen v1 credentials, certificates, cursors or snapshots. Background maintenance prepares the v1.1 cache; no canonical migration occurs.
- **Certificate binding:** retain the certified-generation/current-readiness protocol, but bind accessDigest to the selected owner/readSet and optional ownerGeneration, never per-namespace authority generations or a request-unique credential. Fresh requests can use the same maintained generation (§6.1.1).
- **Preserved:** supervisor/failed-open ownership, bounded acknowledged history and resource quarantine; reader/writer native telemetry; hard deadlines and ≤50 ms public settlement; fresh request lifecycle; pooled fusion, index states/background maintenance/publication checks, WAL, schema split, backup policy and all numerical gates. Only authority-dependent wiring/tests and explicit version identities change. Historical v1 authority tests are replaced rather than carried forward as hidden requirements.


## 1. Purpose, evidence and compatibility boundary

The commercial product wants its ChatGPT `ask_cairn` tool and website search to retrieve Memories and Cards together through `find_memory_candidates`, `fetch_memory_candidate_evidence` and `read_memory_context`. Its private repository is unavailable to this author. The following observations are **product-supplied evidence from a synthetic trial against `b2513501`, Node 24**, not measurements reproduced here:

| Product observation | Consequence for this proposal |
| --- | --- |
| 1,112 Memories across four namespaces; memory-only v18 reads preserved user_version, logical hash and file hash, and the old pin reopened the file. Cards required v23. | Preserve production v18 without canonical migration; distinguish capabilities by physical schema. |
| 52 handwritten Chinese questions, lexical only: recall@5 and recall@12 reported as 92%. | Directional evidence only. Freeze queries and relevance labels before a new recall comparison; Japanese and mixed queries still need coverage. |
| A four-namespace readSet failed `invalid_read_set`; four separate calls summed to 1.36 s at 1,112 Memories and 4.47 s at 3,336. | One authorized projection and one engine ranking must replace product-side fan-out. |
| Initial lexical build took 4.5 s at 1,112 Memories and returned `index_unavailable` at 3,336. | Request success must not depend on finishing index construction in that request. |
| A 50 ms deadline still allowed 0.31–1.06 s loop gaps; every request exceeded the 100 ms main-loop budget. | Isolate native work and counting in a Worker; add a parent-controlled response cutoff. |

Production remains **schema v18**. P2 introduces no canonical migration, DDL, index, trigger, capture hook or writer callback. An explicitly authorized sidecar maintainer is sufficient for memory-only production use. Upgrading canonical storage to enable Cards is a separate product rollout, never a side effect of opening a reader.

Product decisions now fix the deployment posture: **fresh open → read → await close per HTTP request**, including cold runs in the ≤100 ms host-loop maximum; lexical-only default; personal plus at most 31 selected projects; supervised maintenance of the owner-wide Memory+Card `current` and `history` projections. New items must become searchable within 30 s p95 under continuous writes, with ≤1% not-ready requests after initial build. Not-ready lookup falls back in the product to today's Card search plus `recall_memory`, marks coverage partial and adds no user-facing copy. Engine refusal remains truthful and never starts fallback, catch-up or inference itself. Exact latency gates are in §10.

The frozen baseline is [unified-memory-v1-contract.md](unified-memory-v1-contract.md): U5a §13, U2c §14, U5b §§15.1–15.7, the superseding §15.8 representation amendment, and §§17–§20. In particular, §15.8 supersedes earlier §15 DTO examples (`docs/plans/unified-memory-v1-contract.md:1439`, `docs/plans/unified-memory-v1-contract.md:1473`, `docs/plans/unified-memory-v1-contract.md:1608`). No frozen section is edited by this packet.

Only the new product profile changes four execution rules: Worker execution/hard response deadlines (C-1), the readSet bound (C-2), request-time maintenance (C-3), and WAL eligibility/lock handling (C-4). These are explicit opt-in amendments to §13.1, §13.2, §13.4 and §15.1, including §19.4's allowance for final work after a cooperative deadline. The v1.1 request-authority amendment in §4.1 additionally supersedes the stronger authority-vector/lease sampling rules for this profile only. Evidence, canonical/index/dependency currentness, accounting, representation and all other frozen rules remain authoritative; canonical content epochs are not authority generations.

## 3. Version identity and unchanged defaults

Select P2 through **new constructors** with literal `profile:'context-read-product-v1.1'`; retain `version:'context-read-v1'` for the existing data contract. Unknown/missing product profile on these constructors refuses `invalid_input`. Existing `openContextReader`, context-enabled `openMemoryCore`, `openMemoryReader`, tools and CLI defaults do not silently switch execution modes or widen validation.

Without v1.1 selection, preserve byte-identical DTOs, ordering, errors, capabilities, tool descriptions/schemas, prompts and provider-call counts of existing paths. No new default field, background timer, Worker, sidecar probe, environment lookup or network call is introduced in legacy paths. Frozen product v1 is not redefined by this draft. Compatibility golden comparisons normalize only pre-existing nondeterministic fields explicitly identified by the test; metered serializer bytes and tool-list bytes are exact.

Product capabilities additionally identify the profile, execution mode, hard response cutoff, cancellation support, readSet maximum, deterministic namespace-selection policy, ready-only index use, supported schema/type combinations and journal support. Candidate/evidence/assembly success DTOs retain U5a/U5b shapes; namespace truncation uses existing coverage/trace containers as specified in §5. Lifecycle status is a separate host API, not a field inserted into the metered representation. The default product profile is lexical-only, with no embedder constructed or selected implicitly.

Use a separate product sidecar suffix, **`.context-read-product-v1.1.sqlite`**, with independently versioned format 1 and a product-profile marker. This avoids making legacy readers refuse their own cache after product maintenance enables WAL, and avoids mutating old generations in place. No implicit import, conversion, deletion or repair of `.context-read-v1.sqlite` or frozen product v1's `.context-read-product-v1.sqlite`. Product initial construction is an explicitly scheduled build, even if an older sidecar exists. Reuse the storage algorithms and invariants, not legacy file ownership.

Bind product cursors/snapshots to the product profile and canonical readSet in addition to all existing bindings; they are opaque strings with the same bounds. Reject cross-profile cursor/snapshot reuse as `invalid_cursor`/`invalid_snapshot`. Compact item fences retain the existing store-local `snapshot-item` HMAC and eight-character prefix; this profile does not replace that identity or mint new authority.

## 4. Public API and execution boundary — C-1

Proposed core exports (names are part of this draft):

```js
// The host has authenticated this HTTP request, selected its scopes, and minted
// requestCredential bound to this fresh handle/request cutoff in host configuration.
const supervisor = createContextReadSupervisor(); // owned before any async open
const reader = await openContextProductReader({
  supervisor,
  path,
  version: 'context-read-v1',
  profile: 'context-read-product-v1.1',
  readSet,                         // host-fixed, canonicalized once
  ownerCoverage,                  // trusted selection descriptor, §5
  host: { moduleUrl, configuration },
  diagnostics: false,              // literal true opts into native diagnostics
  deadlineMs: 5000                 // opening deadline; 1..5000
}, { signal });                   // HTTP disconnect also cancels opening

await reader.getContextReadCapabilities();
// Alternative calls for the current HTTP request, not cross-request handle reuse:
await reader.getContextIndexStatus({ readSet, types, intent, deadlineMs }, requestCredential, { signal });
await reader.findCandidates(input, requestCredential, { signal });
await reader.contextRead(input, requestCredential, { signal });
await reader.fetchCandidateEvidence({ ...fetchInput, deadlineMs }, requestCredential, { signal });
await reader.close();
// HTTP finally closes a returned handle; service shutdown always also does:
await supervisor.close();          // includes failed-opening resources
```

All methods return Promises of envelopes, including fetch and capabilities. Constructor option validation rejects invalid input before dispatch; operational opening failures reject with a sanitized coded error and opaque `cleanupId` owned by the supplied supervisor. No partially initialized reader escapes. Reader `close()` is idempotent, stops dispatch and awaits actual Worker/native cleanup; successful request lifecycle latency includes that awaited close. Failed-opening resources remain observable through the supervisor even though no reader was returned (§4.4).

`input` and `fetchInput` retain existing strict core grammars and bounds. Query/fetch/status deadlines are positive integers 1–5,000 ms, default 1,000 ms. Fetch gains `deadlineMs` **only on this profile**; it supports existing full refs, aligned internal fences, or snapshot, with their original mutual exclusions. The product tool adapter accepts compact refs under §15.8 and expands them against the immutable startup mapping. The adapter must await fetch and propagate disconnect/abort through the separate `signal` control argument. Signals, tokens and host configuration never become model-supplied tool fields. The P2-only fetch tool schema may expose bounded `deadlineMs`; legacy schemas stay exact.

The trusted host fixes the readSet. Core requests repeat it, accepting permutations that normalize to the fixed set; omission or a different well-formed set refuses `invalid_read_set`. A new selection requires a new handle and mapping, never live reordering of compact `ns` indices. MCP and website adapters inject that fixed set; an LLM cannot supply namespaces, authority, fences, bootstrap modules, maintenance options, providers or ranking configuration.

### 4.1 Request-scoped host authority (`context-read-product-v1.1`)

The product seam review found **1 PASS, 5 MAPPING NOTE and 3 DOES NOT FIT** among the frozen v1 checklist items. Server-side identity/owner binding fits. The product has no per-namespace authority-generation vector, cross-process revocation registry or final-read authority lease. Its bearer is resolved once per HTTP request, and erasure uses maintenance quiescence. These are product-reported findings from a private source review, not implementation or concurrency evidence reproduced here. The primary selected the request-scoped model below; the report's earlier recommendation to build stronger synchronization is not a requirement of v1.1.

`host.moduleUrl` remains a trusted constructor-only local file module loaded inside the fixed engine Worker entry, exporting `createContextReadHost(configuration)`. It supplies synchronous `authorize`/`isCurrent`, optional exact counter and explicitly configured optional provider ports. It opens no migration-capable core. It is host code with host privileges, never an import chosen by request/tool text. An absent counter still permits candidates/fetch and refuses assembly under the existing exact-counter contract. The engine repository's legacy adapter is not evidence that a product authority adapter is already implemented.

#### 4.1.1 Request snapshot, credential and binding

After authenticating the HTTP request and resolving its authorized inventory **before open**, the host mints this logical snapshot:

```text
{ownerId,
 namespaces:{readSet,ownerCoverage},
 issuedAt,
 ownerGeneration?}
```

`readSet` is the frozen selected canonical namespace array and `ownerCoverage` is the exact §5 descriptor. `issuedAt` is a nonnegative safe-integer UTC epoch-millisecond issuance time; it is not a generation or sufficient replay protection. `ownerGeneration`, when supplied, is one positive safe integer for that owner, sampled at request start and bumped by the host on revoke or erase. Do not invent an owner generation when absent, derive it from content epochs, or require a per-namespace vector.

The snapshot travels as a **bounded opaque own-data request credential**, which may reference a trusted binding rather than repeat its contents. Preserve **16,384 UTF-8 bytes, depth 16, 8,192 nodes** and the **262,144-byte total IPC cap**. Reject malformed/oversized credentials as `invalid_input`; invalid, expired, revoked or wrong-request credentials as `authority_required` at entry. No raw bearer, asynchronous caller object, function source, serialized grant or unbounded inventory is forwarded. Credentials never enter model text, logs or public diagnostics.

The host's trusted issuance/validation state binds the credential to a fresh unguessable **HTTP request identity and reader-handle incarnation**, owner, canonical selected mapping, ownerCoverage, issuance/expiry, allowed methods, and the complete operation/payload binding (including fetch fences). The snapshot's public logical shape above does not require exposing that opaque binding. The Worker checks it; cloning a credential is not an allow decision. `authorize` derives the method-specific grant from this one request snapshot, not from independent per-namespace generations. Missing/denied initial authority refuses the whole operation before private counts, scoring, evidence or transmission.

**Lifetime:** a request credential belongs to exactly one fresh HTTP request/reader lifetime. It can accompany that request's permitted engine call, but cannot authorize another request, another independently opened handle, an index maintainer or a maintenance quantum. A new HTTP request reauthenticates and mints a new credential even for the same bearer/owner/readSet. Neither `issuedAt` equality nor knowledge of the owner ID makes an old credential reusable. Request end/disconnect closes admission immediately; supervisor cleanup records can outlive it and confer no new read authority. Restored services invalidate old request bindings before re-exposure; no persistent authority-vector registry is required. Evidence refs/snapshots are data identifiers rather than credentials: a later request can refetch them with **new authentication and a new credential**, subject to their unchanged profile/canonical/item-fence checks.

The trusted handoff fixes an immutable request response deadline no later than **5,000 ms after engine request admission before open**. Existing opening/method deadlines can shorten it, never restart or extend it. Each data/status call uses the earlier of its existing method deadline, the request cutoff and credential expiry; P2 opening/read/status/refresh calls remain capped at 5,000 ms. Public timeout/cancel settlement retains ≤50 ms overshoot; no data is accepted after the cutoff, while close/drain may continue solely to observe native cleanup under supervisor ownership. Cleanup grants no further authority. This prevents multiple calls/opening work from extending a revoked in-flight request's authority window.

#### 4.1.2 Two synchronous currentness checks and exact guarantee

Bearer/session/ACL resolution occurs outside the Worker before issuance. The Worker-local adapter is synchronous, cheap and explicitly configured; it cannot call asynchronous authentication, wait on parent RPC, access the network or await inside `authorize`/`isCurrent`. `isCurrent` checks the request binding against the host-provided request state, including erasure admission and credential-revoked state, plus owner-generation equality when configured. Missing, throwing, Promise-returning or unverifiable state fails closed. With ownerGeneration absent, the erasure/credential checks still apply; absence is not an implicit generation zero or a bypass.

The host must make published revocation/erasure state visible to this cheap synchronous check. A captured `authenticated:true` or owner ID alone is insufficient. Publication here is the product's ordinary credential-revoked/erasure-admission publication, **not** a new pending/effective-vector protocol. The adapter must observe publications preceding its check or refuse when it cannot establish the required local view. This is required adapter wiring, not a claim that the existing product already provides it; it does not require asynchronous reauthentication inside the Worker or a cross-process FIFO.

For each authority-bearing data/status operation the engine samples `isCurrent` exactly twice on a successful path (maintenance uses its separate service authority):

1. **Entry:** after bootstrap/credential binding, at operation entry and **before any index access**, private projection observation, evidence read or provider transmission. A failed entry exits immediately without a second sample.
2. **Final:** once more **immediately before the final canonical read**, outside its transaction, after all preparatory/provider/counter/await work. A changed/denied state now returns `scope_changed` with no data. No authority callback, counter, parent RPC or await occurs inside or after that authoritative read.

Internal guards still enforce immutable request/payload binding, method allowlists, deadlines and canonical/index/dependency fences after awaits and before transmission/publication. They do not introduce per-namespace authority generations or additional async authentication. Optional semantic transmission, when explicitly enabled, uses the same bounded in-flight request authority; this profile does not promise a new synchronized revocation check at every guard. Lexical-only remains the product default.

**Revocation guarantee:**

- An operation whose entry check runs **after a revocation or erasure is published returns no data (`authority_required`)**. Owner-generation mismatch at entry has that same result. No index/statistics/evidence access or fallback data is authorized by that failed credential.
- An operation **already past its entry check may complete only within its own request deadline**. The authority window is bounded by that deadline, **≤5,000 ms for every P2 call**, not by bearer/session lifetime or native cleanup time.
- The second check before final reading returns **`scope_changed` when the state has changed by then**, including an ownerGeneration equality mismatch. It never silently substitutes a new snapshot, owner or generation.
- A revocation published **after the second check**, including between that callback and canonical snapshot acquisition or after the final read, may leave that in-flight request able to complete before its cutoff. There is **no final-read lease or atomic revocation/read interval**. Canonical evidence still linearizes at its final snapshot under the unchanged data/fence rules; this is not the authority-revocation linearization point. No callback after final reading closes that intentionally bounded window.

Revocation is not delayed until native cleanup or a reader release. The host's optional ownerGeneration compares for equality at both samples; a mismatch is authority failure, not index staleness or permission to adopt the new value. Ordinary content epoch changes do not revoke request authority. All native snapshot/refetch/fence checks, exact-revision semantics and hard result cutoff remain mandatory.

#### 4.1.3 Erasure precondition and independent maintenance authority

**Product erasure precondition:** erasure runs under maintenance quiescence with **stopped clients**. Stop new admissions and clients/old reader and maintainer processes, publish erasure denial/revoke credentials, and drain supervised native/provider/resource lifetimes before destructive erasure. Keep restore/admission exposure gates closed until the product's existing maintenance procedure permits serving again. A public timeout or disconnected HTTP request is not proof of native disposal. Do not replace stopped-client/drain requirements with the five-second authority window or a copied denylist. Erasure correctness depends on this product precondition; concurrent erasure with active clients is outside v1.1's guarantee.

A long-lived index maintainer has **its own explicit service authority and supervisor**, configured for its owner/projections and maintenance methods, independent of any HTTP reader credential. It refuses a request credential at construction/use (`authority_required`) even if owner/readSet match; bootstrap discriminates service credentials from request credentials in trusted validation state, never by an untrusted caller flag. Each maintenance quantum has its own ≤5,000-ms budget and synchronous service entry/final checks. Service currentness is checked before private work and immediately before the final post-publication canonical read (§6.1.2); changed service authority returns `scope_changed`. A committed derived artifact may survive a subsequent service-check failure, but grants no reader authority. Cron renewal never extends or lends an HTTP request credential.

Stronger owner/per-namespace generation registries and synchronized final-read revocation are **deferred to a future Cards/teams package**, with their own explicit version and qualification. They are not hidden prerequisites or optional inferred guarantees of v1.1. Supervisor resource tracking remains required and must not be confused with an authority registry.

### Authority seam checklist for the product

This replaces the frozen nine-item checklist with **six adapter checks** for v1.1. The product maps them to its own code before P2a coding; no private implementation is asserted here.

1. **Authenticate, inventory, select:** bind one verified owner before open; enumerate legitimate private/workspace scopes with workspace ACL applied **before** selection. Supply the `lastActiveAt` metadata source (missing=0), canonical IDs and frozen inventory revision for `recent-projects-v1`; denied scopes are not omitted authorized scopes. Public/team Card access retains its own ACL and never changes the private Memory owner.
2. **Worker-local request credential:** mint the bounded opaque snapshot only after request authentication, bind request/handle/owner/readSet/ownerCoverage/payload, and refuse cross-request/handle replay. Provide cheap synchronous Worker-local `authorize`/`isCurrent`, observable erasure/credential state and optional ownerGeneration equality; resolve async auth/ACL outside the Worker. Verify both sample/error boundaries and the intentionally bounded post-check race; no parent RPC or async auth in the Worker.
3. **Lifecycle and disconnect:** register supervisor ownership **before open**, wire failed constructors and existing host resource/drain attribution through confirmed native disposal, await close in HTTP finally and supervisor drain on shutdown. Bind HTTP disconnect to the public abort signal, close request admission, and preserve all bounded-history/quarantine rules.
4. **Error policy and fallback:** map `scope_changed`, `read_timeout`, `reader_failed` and `store_closed` deliberately, preserving internal `read_cancelled`/authority precedence and sanitized diagnostics. Only honest index-not-ready may trigger the agreed partial fallback; fallback **reauthenticates and reauthorizes** through current owner/workspace gates, never reuses a captured owner ID or failed request credential. Authority failure cannot become an empty/partial authorized answer.
5. **Maintenance service:** use separate service authority, methods, budgets and supervisor for the long-lived maintainer; reject request credentials without index access. Keep explicit background work, current/history prebuild and shutdown supervision independent of HTTP lifetimes.
6. **Erasure/restore quiescence:** enforce stopped clients, closed admission and confirmed drain before erase/restore/re-exposure. Invalidate old request bindings and honor current denylist/restore gates; bump ownerGeneration on revoke/erase when that optional mechanism is used. This is a required product precondition, not a claim supplied by an engine read.

### 4.2 Worker ownership and bounds

Reuse/refactor `memory-reader.mjs` dispatch, identity, resource, error, idle and termination machinery behind the new entry; preserve legacy behavior. SQLite-reaching imports remain dynamic behind the established local/CLI boundary, with no `createRequire` escape. Keep the Worker entry fixed, env empty, execArgv empty and output drained. All native open/configure/schema work, canonical/index reads, scoring, tokenization and exact counting run off the host thread.

One in-flight operation per handle, no implicit queue; overlap refuses `read_in_progress`. The reader and maintainer have distinct Workers, so background work cannot occupy the request slot. Retain bounded ranking state, 128 rankings/five-minute TTL and 60 s idle disposal; idle/crash/timeout invalidates retained cursors as `cursor_stale`. A valid durable snapshot can still be canonically refetched after reopening, subject to its fences and profile.

Parent validation inspects own data without executing getters/proxies and caps request/configuration IPC at 262,144 UTF-8 bytes per message; tokens have the stricter §4.1 checklist bound. Data responses still fit the existing 65,536-byte envelope, snapshots 16,384 characters, cursors 8,192 characters and tool transport 262,144 bytes. Reject oversized indivisible data as `context_item_too_large`. Clone/serialization costs and startup/settlement callbacks count toward the host-loop gate; offloading SQLite alone is insufficient. Select Worker heap limits explicitly after auditing the existing 128 MiB vector-cache allowance and counter runtime; do not copy the topic reader's 64 MiB heap blindly.

### 4.3 Hard response deadlines and cancellation

Measure one absolute monotonic deadline from public method entry, including bounded validation, IPC, any lazy restart/opening, authority checks, native waits, scoring, counter work and final canonical revalidation. Also cap it by the immutable request response cutoff from §4.1.1; a second call/restart cannot renew that request window. The parent watchdog owns this deadline independently of Worker progress. Cooperative checks remain useful inside the Worker but do not define the public cutoff. Native cleanup retains its separate ownership lifetime.

On expiry, latch `read_timeout`, discard all later **retrieval results** for that operation/Worker epoch, signal cancellation and request termination. Keep the independent native telemetry channel alive through cleanup (§4.5). **Settle the public call before awaiting termination, no later than deadline + 50 ms.** On AbortSignal, do the same with `read_cancelled`, settling within 50 ms of host-observed abort; pre-aborted calls dispatch nothing. On explicit close, settle active work with `store_closed`, then await cleanup. First terminal event wins; a result received at or after the absolute deadline is a timeout even if the Worker computed it earlier. A result accepted before the cutoff must have completed all frozen final checks. Opening deadlines use the same +50 ms public-rejection gate.

Never deliver a partially refetched evidence list or an assembly whose final validation was cut short. If an ordinary semantic timeout degrades to lexical and a fully validated result arrives before the outer cutoff, retain that frozen channel behavior. Otherwise the entire operation times out. Optional admission may stop early, but required metering/final validation must fit the hard response window or the result is discarded. Do not extend a deadline for a final pass.

“Hard” means a parent-enforced response cutoff and bounded public cancellation independent of native cleanup; it does **not** claim that Node terminates an executing SQLite step at an exact CPU instant. Timers also depend on host scheduling; the ≤50 ms overshoot is nevertheless an acceptance gate, not waived by that caveat. Record settlement overshoot and native cleanup lag separately. Keep resources quarantined until observed termination and provider cleanup settle; do not launch unsafe replacements or free capacity on a timer alone. Reader close and the supervisor's shutdown drain expose actual cleanup, including failed constructors.

### 4.4 Supervisor owns opening failures (audit F3)

`createContextReadSupervisor()` synchronously creates a SQLite-free resource owner before any constructor dispatch. Every product reader/maintainer constructor requires `supervisor`; registration of an operation ID, telemetry buffer, termination promise and cleanup ID happens **before** Worker creation/bootstrap. Every acquired native handle, host resource/drain attribution and optional provider child joins that ownership record immediately, not only after construction succeeds. Constructors accept `{signal}` as their second control argument. Invalid option validation creates no Worker; bootstrap/open timeout and partial resource acquisition enter the same supervised cleanup path as a timed-out read.

The supervisor exposes these host-only operations:

```js
supervisor.getCleanupStatus(cleanupId); // synchronous frozen metadata, no paths
await supervisor.drain(cleanupId);     // await this failed/open/read cleanup only
await supervisor.drain();              // snapshot and await current cleanup records
supervisor.ackCleanup(cleanupId);       // release a drained completed record early
await supervisor.close();              // stop new opens, cancel, then drain all
```

Cleanup status is exactly `{cleanupId,state,workerStopped,nativeDisposed,leasesReleased,providersSettled,telemetry,expiresAt}`, where `state` is `pending|complete|failed`, each disposal field is boolean (true also for a resource never acquired), and `telemetry` is `disabled|pending|complete|incomplete` (§4.5); disabled means diagnostics were not selected. `expiresAt` is null for active/pinned records, otherwise the finite absolute process-monotonic expiry time defined below. Complete requires all disposal booleans true; diagnostic incompleteness is separate and never a zero-busy pass. Unknown or expired cleanup ID refuses `invalid_input`; absence does not assert disposal. Metadata contains no native message, path, owner or token. Opening rejection exposes only the coded error and its cleanup ID; operational failures cannot orphan an invisible Worker. `drain(cleanupId)` waits for that record only; argument-free drain snapshots records already entering cleanup and does not cancel/wait for unrelated healthy HTTP handles or the live pump. `close()` stops all resources owned by that supervisor and drains them. Failure to confirm disposal reports `reader_failed`, never completion from a kill request alone.

The existing `leasesReleased` lifecycle field is retained unchanged for any **outer host resource/drain attribution** used by the adapter, and is true when none was acquired. It does not imply or require an authority lease. Public settlement must not release that attribution, a native resource or provider capacity while its underlying work is still alive. These ownership rules survive the authority revision in full.

All supervisors participate in **one process-wide resource registry**, with fixed global resource limits, not per-request isolated quotas. Register a normalized path/profile/stable-host-ownership-domain key before open, then bind it to validated canonical device/inode identity; aliases of an already identified file share the quarantine. The host ownership domain is resource attribution, not an authority realm/generation registry; it cannot be changed by minting a new request credential or request ID. A pending failed-opening/terminated-operation cleanup blocks replacement opens for that store/domain with `read_in_progress`, even through a newly created supervisor. Unconfirmed failed cleanup latches `reader_failed` for that identity until explicit operator recovery after actual resource disposal; creating another supervisor/handle is not recovery. Healthy independent request handles may coexist within the process-wide limits; the quarantine is not a permanent one-reader-per-store lock.

Service shutdown must close the supervisor even if the HTTP constructor rejected and no handle exists. Its owned termination handlers retain live supervision until cleanup completes/fails; no detached PID/log constitutes supervision. Request settlement and shutdown drain are separate promises: the former meets +50 ms, while the latter awaits native cleanup off the host thread. After a bootstrap failure following resource acquisition, release only confirmed-disposed resources. No ordinary SQLite writer is gated by this registry; monitor any native read-lock lag against existing writer busy/operation bounds.

#### 4.4.1 Bounded cleanup history (revision-2 finding R2-4)

Separate **live/pinned ownership** from **completed history**, process-wide across all supervisors. A handle may create many operation records; only in-flight operations and disposal-dependent pins count as live. Limits cannot reset by creating a fresh HTTP handle or supervisor.

Shared resources have one handle-owned record: a successful constructor promotes its opening record to that owner, and read-operation records borrow its Worker/connections rather than duplicating ownership. A completed read can finalize its own resource-attribution/provider/diagnostic record while a healthy retained handle remains open; “never acquired” disposal fields refer to resources not owned by that operation. A required Worker termination is instead pinned to the shared owner, and finalizing a borrower never releases that owner's quarantine. Apply fixed admission limits to the combined live-owner/operation/pin count, not just live PIDs.

- A record can enter completed history only when actual native/Worker disposal, outer resource/drain release and provider settlement are confirmed and its diagnostic drain is finalized as complete, incomplete or disabled. Retain at most **1,024 completed records**, at most **1 MiB of completed metadata** and at most **16 MiB of completed diagnostic buffers/records**, all process-wide. Each cleanup ID is a never-reused opaque ASCII identifier of at most 64 bytes. These are product-profile limits; no legacy default changes.
- On entering history, set `expiresAt = completionMonotonicTime + 300,000 ms`. Expire at that time, without renewal on get/drain. If a count/byte cap would be exceeded first, evict the **oldest completed record by completion sequence**, including its diagnostics, until within all caps. Thus a completed ID expires at acknowledgement, its time limit or oldest-first capacity eviction, whichever comes first. It may disappear before its displayed expiresAt under capacity pressure. A single completed diagnostic payload over the history-byte cap is exported to its waiting drain consumer, or marked diagnostic-incomplete if it cannot be exported; it is not retained over the cap.
- `drain(cleanupId)` delivers the final status and bounded diagnostic record to the waiting host consumer; repeated calls work only while the history entry remains retained. Concurrent drains share one promise/delivery record per cleanup ID, not a registry list of one waiter per call. A drain that started while the record was live pins delivery through the completion transition, so capacity eviction cannot race that delivery. Delivery is part of the existing bounded active-operation budget, not unbounded additional history; after resolution only caller-owned copies may outlive history expiry. After recording the result, the consumer calls synchronous `ackCleanup(cleanupId)` to remove that completed entry and buffers immediately. Acknowledgement of live/pending records refuses `read_in_progress`, of a failed quarantine refuses `reader_failed`, and of unknown/expired/already acknowledged IDs refuses `invalid_input`. No per-ID tombstone is retained to make repeated acknowledgement appear successful.
- Pending disposal and failed quarantines **never** expire or get evicted for history space. They consume the fixed live/quarantine admission quota until confirmed disposal, or explicit recovery that itself verifies disposal and releases the safety latch. A failed latch needing operator recovery is not cleared merely because telemetry was acknowledged. If the quota is exhausted, refuse new work with the existing lifecycle errors; do not discard a safety record or launch a replacement. After safe recovery, eligible metadata can enter the same bounded history. Registry indexes for empty/closed supervisors are reclaimed; do not keep an unbounded list of old owners, handles, IDs or completed-operation tombstones.
- If finalized diagnostics are evicted/expire before a measurement consumer obtains them, that operation's diagnostic coverage is **incomplete** and its measurement cell is invalid, even if the cleanup state was complete. The measurement parent independently retains its attempt ledger and must drain/ack each operation promptly; it cannot interpret expired IDs as zero native failures. Ack/expiry does not erase already exported raw measurement evidence. Safety disposal and diagnostic completeness remain separate claims.

This bounds both metadata and retained telemetry under repeated fresh open/read/close traffic. Ordinary deterministic tests use a mock monotonic clock and registry counters for expiry/capacity/ack behavior; they do not add elapsed-time or heap-timing gates to ordinary suites.

### 4.5 Native telemetry independent of result delivery (audit F5)

When diagnostics are selected, create a parent-owned, bounded shared telemetry buffer **before opening** and attach it to the supervisor operation. It survives discarded retrieval messages, constructor rejection and Worker termination. Native wrappers synchronously record a begin marker before each native open/prepare/execute/iterator/transaction/close call and an outcome marker immediately on return/throw, **before** public error mapping or `postMessage`. Every failure records only fixed stage/statement labels, numeric primary/extended SQLite codes and a monotonic event sequence. Never include SQL, native messages, paths, content, owner/namespace/entity IDs or tokens. Retrieval and telemetry have separate acceptance paths; a late retrieval result is still discarded.

Use atomic committed counters for total calls begun/completed, failures, native primary 5 and 6, in-flight native calls and overflow/lost outcomes; retain the corresponding sanitized failure records in a bounded ring. Each outcome publishes atomically after its record is committed. The parent never infers zero from an empty message queue. Telemetry tags bind operation ID, Worker epoch and diagnostic-protocol version; malformed/mismatched frames fail diagnostic completeness. Counter overflow or missing ring records is explicitly incomplete, not sampling. The implementation fixes/advertises buffer capacity before measurements and cannot grow it after seeing failures.

The supervisor drains after Worker/native/provider shutdown, reading committed shared state even if no result envelope arrived. Coverage is `complete` only when every begun native call has a committed outcome, no native call remains in flight, all records through the final committed sequence are present, no overflow/loss occurred, and termination is confirmed. Termination during an unreturned native call, a crash inside recording, or a missing diagnostic acknowledgement makes coverage `incomplete`; known busy events still count, but the cell cannot claim zero. A `BUSY` recorded just before the response cutoff therefore survives the subsequent `read_timeout`; if termination prevents observing the native outcome, the cell is **invalid** rather than zero-busy. Cleanup itself may be complete while diagnostic coverage is incomplete.

This telemetry is host/operator metadata, never a model text block or new evidence field. Measurement uses the union of public errors and retained native failures, with de-duplication by operation/event sequence; incomplete diagnostic coverage prevents acceptance even if all public responses were fast. Production diagnostics remain opt-in and legacy paths remain byte-identical.

#### 4.5.1 Independent-process writer telemetry (revision-2 finding R2-3)

The zero-busy gate includes ordinary writers in independent processes; reader/maintainer supervisor telemetry cannot certify their native outcomes. The reused writer harness currently observes successful COMMITs and surfaced failures (`tools/testing/measure-topic-reader-wal.mjs:124`, `tools/testing/measure-topic-reader-wal.mjs:146`); that is **not** complete pre-mapping native telemetry. Extend the opt-in harness with the following separate writer observer, without changing ordinary write defaults, busy policy, retries, transaction behavior or static SQLite-free import boundaries.

1. The measurement parent allocates an expected writer stream/epoch before spawn. In the writer process, install the observer at the native SQLite boundary **before the first writable opener/import path can acquire a connection**. An armed handshake confirms the fixed diagnostic protocol, native-call coverage and bounded journal capacity before the parent permits work. Missing arming, an uninstrumented opener/connection or an unsupported interception boundary makes coverage incomplete; no public result can substitute for it.
2. Observe native connection creation/open/configuration, prepare, cached statement execution and iterator steps, BEGIN/COMMIT/**ROLLBACK**, and every close/disposal path. This includes failed opening, per-request open/write/finally-close, retained opening/final shutdown, internal failure handling and any existing retries. For each call, synchronously increment begun/in-flight counters before invocation and commit its outcome after return/throw, **before ordinary storage/public error mapping**. Preserve the original exception/outcome. Record sanitized stage/statement labels, numeric primary/extended SQLite failure codes and successful in-call commits; do not infer raw failures solely from a caught public error. Label lifecycle phases separately so opening commits never count as write-call exposure.
3. Use a bounded process-local diagnostic journal, with one monotonic sequence across operation-boundary records and failure records, and cumulative begun/completed/in-flight/failure/busy/overflow counters. The parent assigns expected operation IDs for fresh write lifecycles; retained open/shutdown have their own expected lifecycle records. Correlate raw events to these opaque IDs/epochs, never content or namespace identifiers. The observer stores records synchronously; it neither waits for IPC nor invokes callbacks/awaits inside a SQLite transaction. Outside the public operation, transfer bounded sequenced chunks to the parent over a dedicated diagnostic message type, separate from the ordinary writer result/progress stream.
4. The parent acknowledges only a contiguous, validated sequence and matching monotonic counter watermarks. The writer retains unacknowledged chunks within its pre-registered capacity and may resend identical chunks outside transactions; the parent de-duplicates by stream/epoch/sequence. These are diagnostic-transfer resends, **not** public write retries. Overflow, sequence gaps, conflicting duplicates, incorrect epoch, dropped/malformed chunks or inability to record an outcome set incomplete coverage. No oldest-record overwrite or sampling is allowed to claim completeness. Capacities cannot be tuned after observing a run.
5. After all ordinary and finally/shutdown closes, the writer sends a final diagnostic seal containing its last sequence, expected operation range, cumulative begun/completed/failure/busy counts, zero in-flight calls, overflow/loss flags and disposal outcome. Wait for acknowledgement of every chunk and seal before disconnecting normally. The parent drains through the seal and observes actual process exit/disconnect; an IPC send callback, clean public result or live PID alone is insufficient. A crash/forced stop before a complete seal, lost final acknowledgement, unreturned native call or missing expected operation makes the writer's coverage incomplete. Keep every already observed failure even on an incomplete stream; never fill missing intervals with zero.

Measurement acceptance requires **both** complete reader/maintainer operation coverage and complete writer stream/lifecycle coverage, including baseline writers and final drain. A native writer BUSY hidden by a public `storage_error`, `unsupported_database` or other sanitized code still increments native primary 5/6 and fails the normal WAL zero-busy gate. Missing writer telemetry invalidates its cell independently of reader success or observed commits. The parent's raw attempt/diagnostic ledger outlives supervisor history expiry; export/ack promptly under §4.4.1. Writer observation is opt-in synthetic instrumentation, not a canonical hook or new product request API.

## 5. Owner-wide readSet and deterministic fusion — C-2

The shape stays an array of full namespaces:

```js
[
  { ownerId, scope: 'personal', projectId: null },
  { ownerId, scope: 'project', projectId: 'project-a' },
  { ownerId, scope: 'project', projectId: 'project-b' },
  { ownerId, scope: 'project', projectId: 'project-c' }
]
```

Engine maximum: **32 distinct selected namespaces**, one owner, at most one personal namespace and **at most 31 projects**. A nonempty project-only subset or personal-only set is legal. Every namespace uses existing identifier/namespace rules. Reject duplicate, mixed-owner, malformed, sparse, accessor/unknown-field or oversized **selected readSet** input as `invalid_read_set` before sidecar work. An owner with more projects is supported by the deterministic partial-selection contract below, not by silently truncating an oversized engine request. “Owner-wide” means the host's authorized enumeration, not automatic discovery or permission to read every project belonging to an owner.

**Overflow selection policy `recent-projects-v1`:** the host derives the authorized project inventory from its own metadata, retains personal if it is in the requested authorized inventory, and chooses at most 31 projects by descending `lastActiveAt` (integer UTC epoch milliseconds; missing is 0). Ties use ascending UTF-8 project ID bytes. Activity is host project metadata, never inferred by request-time content/index scans; the selection revision freezes that inventory/activity snapshot for the request and matching maintenance projection. Compute/cache this ordering off the host main thread or use a bounded indexed metadata selection; do not synchronously sort an unbounded heavy-owner inventory in an HTTP callback. Selection is independent of query, incoming enumeration order and model output. No namespace priority/quota is applied inside the selected projection's ranking. Access filtering precedes selection; denied namespaces are not counted as omitted authorized projects.

The trusted constructor field is exactly `ownerCoverage:{policy:'recent-projects-v1',selectionRevision,requestedNamespaces,selectedNamespaces,omittedNamespaces}`. `selectionRevision` is a host-issued nonempty bounded identifier (≤200 UTF-16 units); counts are nonnegative safe integers, selected equals `readSet.length`, requested equals selected + omitted, and requested is at least one. When omitted is nonzero the selected list contains all requested personal scope (if any) plus the first 31 authorized projects under the frozen ordering; when zero no requested namespace is omitted. Authority request binding includes the descriptor/profile as immutable constructor configuration together with the complete existing method payload; it is not a new model-supplied input field. The host verifies selection against its inventory; the engine validates descriptor consistency and does not discover excluded projects or read their statistics. The engine request remains bounded even for a heavy owner's larger inventory.

If `omittedNamespaces>0`, candidate `coverage.status` and assembly `diagnostics.candidates.coverage.status` are **`partial`**, even when selected-projection lexical coverage is complete. Existing `trace` carries exactly `namespaceSelection:{...ownerCoverage}` (under `diagnostics.candidates.trace` in assembly); no new metered fields or full omitted-project list are added. Complete-empty for the selected set cannot claim complete-empty for the owner. Lifecycle coverage explicitly reports these same counts (§6.1). Exact evidence DTOs stay `{items,snapshot}`; product HTTP/tool metadata reports the same selection descriptor/partial status outside model text, never rewrites identities or claims an exhaustive owner result. The product does not perform namespace RRF.

Product overflow behavior is therefore deterministic partial coverage, not an error or an unannounced drop. The raw selected readSet cap still protects the engine. A selection change opens a fresh mapping/handle and requires a maintained matching projection; if it is not ready, product fallback is partial. Prebuild active selections and record selection churn; overflow selection may not be used to evade the four-namespace full-coverage gates.

Canonicalize with the existing UTF-8 namespace-key ordering, preserving the current mapping for existing one/two-namespace inputs. Both facade and sidecar projection validation use the new profile-aware validator and the exact owner/request-selected mapping. The optional ownerGeneration is a scalar; no per-namespace authority-generation vector is constructed or sorted. No namespace may be dropped silently. Authorization refusal fails the entire call; no partial authorized subset is inferred.

The **ranking rule is pooled projection ranking**, extending today's engine rule, rather than adding a second RRF over namespaces:

1. Construct the exact authorized union for normalized `(readSet, types, intent)`. Use one complete eligible-projection N, total token length and term df. Score every matching document with frozen T1/BM25 constants. Sort descending score, then binary canonical `(owner,scope,project,type,id)` tuple. No per-namespace top-k truncation before this score/rank.
2. If explicitly enabled semantic preflight is complete over that entire union and within existing vector/resident-byte bounds, embed the query once and score the full authorized vector set. Sort cosine ties with the same tuple. Never dispatch one embedding per namespace or fuse incomplete semantic coverage.
3. Fuse the **global lexical and global semantic lists once**, using the existing family preset: local `rrf-k60-d12` or hosted `rrf-k10`. Score is `sum(weight / (k + oneBasedChannelRank))`; absent membership contributes zero. Sort fused score descending with the same canonical tuple tie-break; retain the existing 24-item horizon, default limit 12 and maximum 24. Disabled/degraded semantic preserves global BM25 order.
4. Freeze this single ranking for continuation; namespaces do not receive quotas, weights or a priority based on input order. Equal bodies remain separate typed identities. ReadSet permutations cannot change ranks, compact namespace indices, statistics, snapshots' scope binding or results.

This is the deterministic engine fusion across namespaces: one pooled lexical/semantic universe followed by the established channel fusion. The product performs no RRF, score normalization or merging of namespace responses. P2 adds no new tokenizer, substring fallback or quality claim. Explicitly test the frozen one-character Han known miss separately from regression failures.

The initial product profile exposes baseline Memory/Card lexical retrieval, with semantic disabled and owner approval pending; the optional configured semantic seam retains its frozen semantics when explicitly enabled later. Optional relations/MOC, role reads, assets and Raw search are not enabled by P2. Source/profile requests unavailable on the product handle refuse `invalid_input`; legacy separately opted-in paths remain unchanged. Card current-dependency checks on schemas that contain them remain mandatory even without optional retrieval sources; background maintenance must observe their extra fences before statistics/publication, per frozen §19.4.

## 6. Index lifecycle and maintenance — C-3

### 6.1 Lifecycle and visibility

Readiness is **per exact normalized readSet/types/intent projection**, tokenizer/representation, store/profile identity and access/canonical/dependency fences. A ready single-namespace index does not imply a ready four-namespace index. The host pre-registers/builds projections it plans to query; unforeseen combinations return unavailable until explicitly maintained. Requests never manufacture aggregate statistics from incomplete shards.

`getContextIndexStatus` is an authorized, Worker-backed observation only, with the same hard deadline and fixed readSet. Its strict input is `{readSet,types,intent,deadlineMs?}`. Authority explicitly allowlists this method and binds the full input before any projection observation. Its success envelope has **exactly** this host-only DTO; all displayed fields are present, no additional keys, and this is not model text:

```text
{profile:'context-read-product-v1.1',
 lexical:{state,reason,progress},
 semantic:{state,reason},
 coverage:{status,freshness,byType,namespaces}}

progress = null | {phase,checkpoint,sequence,baseSequence}
byType = {memory?:{eligible,indexed,embedded}, card?:{eligible,indexed,embedded}}
namespaces = {policy:'recent-projects-v1',selectionRevision,
              requestedNamespaces,selectedNamespaces,omittedNamespaces}
```

`byType` has exactly the requested type keys in Memory/Card order, never unsupported types. Every count is null or a nonnegative safe integer. Progress phase/checkpoint/baseSequence are nonnegative safe integers, sequence is positive, and `baseSequence<=sequence`. Progress is the latest **validated durable checkpoint**, not speculative in-flight work; phase is the completed scan-stream count or current stream ordinal under the format's fixed stream order. Namespace fields equal the constructor descriptor. Lifecycle lexical `state` is exactly `absent|building|ready|stale|catching_up|unavailable`; no liveness is inferred from it.

| Lexical state | Exact reason / progress | Exact coverage and counts | Request behavior |
| --- | --- | --- | --- |
| `absent` | `reason:'missing'`; progress null. No generation/checkpoint exists for the projection. | `status:'unavailable',freshness:'unverified'`; all type counts null. | `index_unavailable`, no create/build. |
| `building` | `reason:'initial_build'` or `'rebuild'` from the checkpoint's fixed build kind; progress nonnull, baseSequence 0. | `unavailable/unverified`; all type counts null. | Incomplete first/rebuild work is not searchable. |
| `ready` | reason null; progress nonnull, certified publication **matching fresh current-fence checks**, not merely committed. | `status:'complete'` iff omittedNamespaces is 0, otherwise `'partial'`; freshness `'current'`. Eligible/indexed from the validated record and equal; embedded follows semantic rules below. | Search selected projection; whole-owner coverage remains partial on overflow. |
| `stale` | No valid resumable delta checkpoint for the current fences. Reason first mismatch in priority `access_changed`, `dependency_changed`, `fence_changed`; progress is old validated publication progress, or null if it cannot be trusted. | `unavailable/stale`; all type counts null. | `index_unavailable`; affected continuation is `cursor_stale`. |
| `catching_up` | Valid **durable incomplete delta progress** with baseSequence>0 against the current target fences; `reason:'resume_pending'`, progress nonnull. | `unavailable/stale`; all type counts null. | Unavailable until full publication; does not mean a task is currently running. |
| `unavailable` | First applicable reason in priority `wrong_store`, `incompatible`, `corrupt`, `validation_missing`, `validation_invalid`, `storage_unavailable`; progress null. | `unavailable/unverified`; all type counts null. | No request repair/deep scan. Unsafe canonical files keep existing opener errors instead of this DTO. |

Coverage status is exactly `complete|partial|unavailable`; freshness exactly `current|stale|unverified`. Missing checkpoint alone means absent; missing validation evidence on an apparently published generation means unavailable/validation_missing. Invalid HMAC/bindings mean validation_invalid; an observed native corruption signal means corrupt. If a checkpoint's target stable accessDigest or canonical/dependency vectors no longer match, classify stale rather than resumable. File/format identity failures take unavailable precedence over stale. A read handle closed/discarded returns `store_closed`, with **no success DTO**, not a synthetic closed-state status.

Semantic lifecycle is exactly `{state:'disabled',reason:'not_enabled'}` for the default product profile, even if a provider is merely configured; every embedded count is null. On an explicitly enabled semantic profile, use `{state:'absent',reason:'not_configured'}` without a provider, `{state:'stale_index',reason:'index_not_ready'}` when lexical is not ready, `{state:'unavailable',reason:'provider_unavailable'}` for an unavailable selected provider, `{state:'partial_coverage',reason:'missing_vectors'}` for an otherwise ready incomplete vector publication, or `{state:'ready',reason:null}` for complete validated coverage. This listed order resolves simultaneous conditions. Embedded counts are known only from a matching certified vector manifest; otherwise null. Semantic lifecycle readiness does not authorize transmission or promise an attempted provider call.

These states describe durable work, not active execution: after a maintainer crashes or stops, valid initial progress remains `building` and valid delta progress remains `catching_up/resume_pending`, with unchanged checkpoint. A reader restart produces the same status from the same records/fences; no heartbeat or still-live PID is required. No read/status call persists a marker, renews a task or queues repair. Only an explicit refresh resumes work.

Incomplete lexical generations remain unavailable. Overflow partial coverage (§5) describes selected namespace scope and does **not** permit searching incomplete indexes. Lexical-ready/vector-incomplete reads with explicit `semantic:true` retain existing `partial_coverage` degradation and zero query embedding calls. Maintenance may return `partial`; neither partial nor unavailable is “no matches.”

#### 6.1.1 Published validation handoff (audit F2)

The product sidecar format adds immutable published lexical generations and a keyed `validation_records` table plus one projection publication pointer. The maintainer alone creates records after deep integrity/statistics/eligibility verification. A fresh/restarted reader must consume an already certified generation successfully **without another maintenance call** or deep scan. A certificate is evidence of cache validation, never authority to read canonical data.

One lexical validation record is a closed, canonical-JSON object, maximum 16,384 UTF-8 bytes:

```text
{version:'context-index-validation-v1',profile:'context-read-product-v1.1',format:1,
 storeId,canonical:{device,inode,applicationId,userVersion,schemaVersion},
 sidecar:{device,inode,incarnation,schemaVersion},
 projectionDigest,accessDigest,canonicalFenceDigest,dependencyFenceDigest,
 tokenizer,representation,
 generation:{id,sequence,checkpoint,incarnation},publicationId,manifestDigest,
 counts:{byType:{memory?:{eligible,indexed},card?:{eligible,indexed}},
         documents,terms,totalTokenLength},mac}
```

All IDs are nonempty ≤200-unit strings; generation IDs are opaque digests/identifiers rather than the entire serialized namespace array. Positive/nonnegative integers follow the status rules. Device/inode are canonical decimal strings from the safe descriptors. Digests and mac are full 43-character base64url HMAC/SHA-256 values, not compact fence prefixes. `projectionDigest` binds canonical selected readSet/types/intent and profile; activity selection provenance belongs to request coverage rather than lexical statistics identity. In v1.1, `accessDigest` is SHA-256 over canonical JSON `{profile:'context-read-product-v1.1',ownerId,readSet,ownerGeneration}`, with ownerGeneration the optional positive integer or **null when not configured**. It contains **no per-namespace authority vector, request/handle ID, credential, issuedAt, request deadline or service-grant ID**. Canonical/dependency digests still cover all frozen required content/support/currentness fences; content epochs are not authority generations. Manifest digest covers the verified lexical manifest; counts agree with it. No body/source text, vectors or plaintext namespace list enters the record.

Reader request authority and maintainer service authority independently authorize the same selected owner/projection; they do not share a credential. Use the same configured ownerGeneration value/presence in their stable certificate binding. When the optional mechanism is enabled, a changed owner generation makes an older certificate access-stale (`access_changed`) for a **new valid** credential; mismatch of the credential's own ownerGeneration at either currentness check is instead `authority_required`/`scope_changed`. When no generation is configured, all otherwise equivalent fresh requests use null in the digest, so fresh issuance does not force catch-up or a deep scan. Never key persisted certificates/checkpoints or opaque evidence snapshots to a request-unique credential. The snapshot's existing access binding uses this stable digest; canonical/item fences and fresh request authorization remain mandatory.

Compute `mac` over the canonical record without mac using the existing store-local secret in the distinct `context-read-product-v1.1/validation` HMAC domain. This is store-local integrity binding, not new provider key access. Table/format and canonical schema-version checks must be physically attested; device/inode checks bind open descriptors, not path strings. Platforms with a different stable file identity require an explicitly qualified equivalent and protocol revision; the launch gate uses Linux device/inode.

For these records, canonical JSON recursively sorts object keys by UTF-8 bytes, preserves canonical namespace/row-array order and emits exact safe integers; hash UTF-8 bytes with SHA-256, no implicit Unicode normalization. The lexical manifest streams the format-defined document tuples (typed canonical identity, revision/bodyRevision, eligibility, representation and token length), then posting tuples (same identity, term, frequency), then statistics tuples (term, df, N and total length), ordered by canonical identity and term bytes within each table. The maintainer verifies row joins/counts/statistics before hashing; a mere hash of unchecked tables is insufficient. The reader authenticates the recorded digest/bindings and does not re-stream tables.

Incomplete checkpoints have a separate closed record, ≤4,096 UTF-8 bytes: `{version:'context-index-progress-v1',profile,storeId,canonicalIdentityDigest,sidecarIdentityDigest,projectionDigest,accessDigest,canonicalFenceDigest,dependencyFenceDigest,generation:{id,incarnation},kind,progress,mac}`. Identity digests bind the same file/schema identities above; kind is exactly `initial|rebuild|delta`, progress has the exact §6.1 fields, and mac uses the distinct `context-read-product-v1.1/progress` domain. Commit it atomically with the corresponding durable batch/verification checkpoint. Status verifies this one keyed record before exposing progress; it never claims certified searchable counts from it. A missing/invalid record on apparent incomplete work is unavailable/validation_missing or validation_invalid, not fabricated progress. This provides durable crash/reopen status without a deep scan or liveness heartbeat.

Build/catch-up uses a separate staging generation. Published lexical documents/postings/statistics are immutable; background changes never mutate rows under a live lexical certificate. Deep validation can checkpoint bounded verification progress against an unchanged staging manifest. The final **sidecar-only** transaction atomically installs the complete captured generation, full validation record and projection pointer under the maintenance call's independently authorized service grant, after the final pre-commit canonical/dependency fence check. A kill before this commit leaves the previous pointer or an incomplete checkpoint; it cannot install a publication without its matching certificate. The certificate attests the verified captured generation, **not present request readiness** (§6.1.2). Ordinary canonical commits may race the sidecar COMMIT; there is no authority lease or cross-database atomicity. Exactly one coordinated maintenance writer owns a projection; every structural/data update invalidates affected validation evidence or replaces it atomically. An independently certified vector manifest binds the same lexical publication and exact embedder identity; vector refresh cannot invalidate or rewrite unchanged lexical statistics under a certificate.

After per-call authorization, a reader performs only: safe descriptor/identity and scalar physical-format/schema checks; one keyed projection-pointer lookup; one keyed validation-record lookup; bounded decoding/HMAC/binding comparison; scalar canonical/access/dependency fence probes over ≤32 namespaces and existing declared-dependency bounds; and scalar comparison of pointer/generation/publication/checkpoint/incarnation. Read pointer/record/generation in the same sidecar read transaction and recheck publication/fences before final delivery. Counts come from the authenticated record, not request-time COUNT/postings/statistics scans. Reuse a valid record across fresh handles; no process-local warm certificate is required. Treat missing/mismatched record as honest unavailable.

Readiness invalidators are explicit: canonical file/store/schema identity or required restore rebuild; sidecar file identity/incarnation/schema/format; selected projection/types/intent; stable accessDigest including optional ownerGeneration; tokenizer/representation; canonical/dependency fence; publication/checkpoint/generation pointer; invalid record MAC/manifest binding; or an observed native corruption signal. A current-fence mismatch makes an otherwise intact certificate **stale for requests**, not a false attestation of its captured generation. Missing/invalid structural or cryptographic bindings remain unavailable, with the exact §6.1 reasons. Changes unrelated to the projection do not invalidate readiness. Same-database DML is trusted only through the coordinated maintenance writer; arbitrary same-user edits/undetected bit rot are not certified by a one-row read. SQLite read errors refuse and schedule **no** repair. This trust boundary cannot bypass canonical final refetch or either request/service currentness check. Recommended restore rebuilds sidecars, so copied certificates never become ready merely because they were backed up.

#### 6.1.2 Captured certification versus current readiness (revision-2 finding R2-1)

Let **E** be the exact captured canonical/dependency fence vector and verified eligible projection used by a certificate. Certification means its immutable documents/postings/statistics (and separately certified exact-identity vectors) agree with that captured generation. Readiness means those bindings **also match a fresh current canonical snapshot and stable accessDigest at final validation**, under the request or service grant that passed its two currentness checks. There is no cross-database atomic commit and no persistent “currently ready” bit. Neither a valid certificate nor a successful sidecar COMMIT alone establishes readiness. This content-readiness check adds no synchronized authority-revocation guarantee beyond §4.1.

Before installation, maintenance must actually verify the complete staging manifest against E and make its prescribed last fence check; it must never relabel E's data or vectors as E+1. If that check already observes a changed vector, retain/discard the staged work under the existing resume rules rather than knowingly installing it as current. However, the following race is explicitly permitted: check E; an ordinary WAL writer commits E+1; the sidecar commits E's certificate and pointer. The resulting publication is **certified for E and immediately stale**. Holding a canonical read snapshot cannot prevent that ordinary WAL commit. Such a publication is not a corrupt certificate, but **no stale generation is accepted as ready**.

Refresh completion is defined by this post-installation protocol, within the same hard operation deadline:

1. Under the maintenance call's independent service authority, complete all provider awaits, preparatory callbacks, accounting and diagnostic sampling, and confirm the sidecar commit outcome. Then run the **second synchronous service isCurrent check immediately before** the fresh final canonical transaction; changed/unverifiable service state returns `scope_changed`. There is no lease across installation/final validation, and no further host callback after that final sample/read. A committed artifact may survive a later authority failure/timeout/error; do not claim that public failure rolled it back or granted reader authority.
2. End every older canonical read transaction used for the pre-installation check, then start a **new deferred canonical transaction**. Its first actual canonical read acquires a fresh post-sidecar-commit snapshot; do not reuse the snapshot that observed E before installation. Under this snapshot compare all required canonical/dependency fences and physical/store bindings with the certificate, and verify the matching sidecar publication pointer/record under a sidecar read transaction. Use the certified counts, not deep scans. No host callback/provider/await occurs in these final transactions or after final reading.
3. **Refresh success linearizes at acquisition of that post-commit canonical snapshot**, conditional on the entire bounded comparison and both read transactions completing successfully before the public cutoff. For lexical mode, `status:'complete'` requires a matching complete lexical publication at that point. For embedding mode it additionally requires complete matching vector coverage for the selected identity at that same point; lexical-ready/vector-incomplete remains `partial` under the existing channel rules.
4. If the fresh snapshot sees E+1 while the installed certificate is for E, refresh returns successful **`status:'rebuilding'`**, with existing `coverage.status:'unavailable'`, `freshness:'stale'`, unknown current eligible/indexed counts null, and its actual durable publication progress. `getContextIndexStatus` reports stale (or a valid newer catching_up checkpoint); candidate/assembly reads return `index_unavailable`. No request searches the stale generation or repairs it. A native failure/abort/timeout instead keeps its own error; no incomplete comparison yields complete. A later explicit maintenance quantum may reconcile E+1.
5. If the post-commit snapshot still sees E, complete is truthful at that linearization point; a writer committing afterward can make subsequent operations stale without retroactively invalidating this completion. Every later status/read independently performs current-fence checks; it must not trust refresh's earlier complete response. Readers apply their existing final canonical/authority revalidation, not a maintenance-created readiness flag.

A no-op refresh that needs no new publication skips sidecar writes but applies the same final fresh-snapshot comparison to the existing certified pointer after its last maintenance work. It does not manufacture a new certificate or report complete from cached readiness. A status call likewise reports readiness only against its current canonical snapshot; the statement that refresh completed earlier is not validation evidence for that status call.

These rules apply even if a newly installed stale pointer displaced an older publication. They permit captured-generation certification, not stale service or altered authority guarantees. The deterministic rendezvous injects the ordinary writer **after maintenance's final pre-commit fence check and before sidecar COMMIT**, verifies the intact E certificate survives, then verifies post-commit refresh/status/read report E+1 staleness until explicit catch-up.

### 6.2 Explicit background API and budgets

```js
const maintainer = await openContextIndexMaintainer({
  supervisor,
  path, version: 'context-read-v1', profile: 'context-read-product-v1.1',
  readSet, ownerCoverage, host: { moduleUrl, configuration },
  sidecarJournalMode: 'WAL',        // required: 'DELETE' or 'WAL'
  deadlineMs: 5000

await maintainer.refreshContextIndex({
  readSet, types, intent,
  mode: 'lexical',                  // required: 'lexical' or 'embeddings'
  budget: { maxItems: 1024, maxMs: 5000 }
}, serviceCredential, { signal });
await maintainer.getContextIndexStatus({ readSet, types, intent, deadlineMs }, serviceCredential, { signal });
await maintainer.close();
```

The maintainer opens the **canonical database read-only** and only the product sidecar writable. It never constructs ordinary `openMemoryCore`, migrates canonical v18, changes canonical journal mode or installs hooks. Its separate service authority explicitly allowlists `refreshContextIndex` and refuses HTTP request credentials (§4.1.3). Read handles do not expose refresh; maintenance is neither an MCP tool nor a lookup fallback.

One refresh is one bounded quantum: `maxItems` 1–1,024 transformation/embedding attempts, `maxMs` 1–5,000 including opening/validation needed by that call, native waits, scans, checkpoint/publication and inference. Parent cutoff/cancellation follows §4.3. Existing batches cap at 128 rows/2,000,000 text units, with provider-aware single-document local batches where §20 requires them. Scanned metadata, support/dependency lookups and text bytes are independently metered; item caps alone do not bound scanning cost. No unbounded “drain until complete” call is exposed.

`mode:'lexical'` builds missing storage or catches up changed metadata/text and never calls an embedder, even when one is configured. `mode:'embeddings'` requires an independently explicit provider and maintenance policy/budget; it operates only on an already ready lexical projection, otherwise returns `rebuilding`/unavailable without implicitly performing lexical work. It embeds missing exact-identity document vectors outside transactions and revalidates immutable service-grant binding, deadline and canonical/index fences after every await and before each commit; service currentness has the entry/final samples in §4.1.3. Missing vector state never triggers implicit embeddings in a read.

Reuse checkpoint/replay and metadata-merge machinery. Put deep integrity/statistics verification, first schema creation, repair, full build, tokenization and catch-up in maintenance Workers. Read requests perform only bounded read-side identity/format/publication/freshness verification and ready-index lookup; never DDL, `quick_check`, full statistics consistency scans, tokenization of canonical document corpora, writes or repairs. Use §6.1.1's durable validation handoff: construction without a projection token does not read private counts, and an authorized fresh reader can validate the published record without maintenance. A new uncertified generation remains unavailable; an already certified one does not become unvalidated merely because the HTTP reader is fresh.

Checkpoints atomically commit sidecar documents/postings/statistics/vector changes and matching progress. Certify only a complete verified captured projection under independently checked service authority; ordinary canonical/dependency changes invalidate **readiness** at canonical commit, including feature-off writers and other processes. Service revocation has the bounded entry/final-check semantics of §4.1.3, not synchronized exclusion during publication. An immediately stale certified publication is allowed under §6.1.2; **no stale generation is accepted as ready**, and no partially updated statistics score. Killing an uncommitted batch leaves replayable work; committed checkpoints survive. Reuse valid unchanged text/vector identities, never relabel vectors across canonical revisions, captured generations or embedder/representation identities.

The product explicitly schedules maintenance from its per-minute maintenance cron (a product-internal endpoint). Prebuild **`types:['memory','card']` × `intent:'current'|'history'` × selected owner-wide readSet** before enabling context search. Production v18 prebuilds the two Memory-only projections; a deliberate v23+ rollout builds mixed projections before switching types. No request silently downgrades an unsupported Card capability to Memory-only.

The cron entry renews an **owned supervised background maintenance pump**, separate from HTTP read requests. The host configures its cumulative `maxItems`/`maxMs` budgets per minute plus each refresh's existing ≤1,024/≤5,000-ms quantum; repeated quanta round-robin both intents and active selected projections. It observes epochs at intervals **≤5 s** while explicit service authority and total budget are active; every quantum is separately bounded and no HTTP request credential authorizes the pump. Cron renewal hands off without a gap or duplicate projection writer; idle checks are explicit maintenance work, never lookup triggers. The host fixes cumulative quotas, renewal/overlap policy and Worker capacity before measurement; budget exhaustion is visible and cannot reset counters by restarting a handle. Stop/reschedule on failure with durable progress and verified supervision; a detached OS task/log is insufficient.

A single quantum once every 60 s cannot establish 30 s p95 freshness. The supported cron integration must therefore run/supervise work between ticks, with enough budget to pass **new Memory/Card searchable ≤30 s p95 under continuous writes** and **≤1% not-ready after initial build**. If the product's HTTP hosting cannot own that pump, it needs an explicitly owned maintenance service; those gates remain unmet until that exists. Do not weaken fences, hide unavailable outcomes behind fallback, or move work onto a read to pass. The supervisor owns pump shutdown and failed-opening cleanup. Reader startup/requests never start or renew it.

For `index_unavailable`, the product **reauthenticates and reauthorizes** through its existing Card search plus `recall_memory` gates and marks the overall result **partial**, without new user-facing copy. A captured owner ID/request credential is not fallback authentication. Keep the engine outcome/not-ready counter even if fallback returns useful text; fallback is not a successful engine retrieval or complete owner coverage. Authority/lifecycle failures must not be converted to an authorized empty/partial response.

Maintenance success retains `{status,progress,coverage,channels}` with `status:'rebuilding'|'partial'|'complete'`. Completion refers to the fresh post-commit snapshot defined in §6.1.2, not sidecar commit time or a promise of future readiness. A certified but already stale generation yields rebuilding with unavailable/stale coverage. Timeout/abort may occur after a durable checkpoint/publication, so callers inspect status on a later explicit call rather than assuming rollback of all previous progress.

### 6.3 Embeddings and shared accounting

The default product profile is **lexical-only**. `semantic` remains opt-in and false by default, and the embedder remains configurable but off/unconstructed by default. Enabling semantic search is pending the owner's decision. A configured provider/key alone does not enable it. An explicitly enabled semantic read may make the existing **one query embedding** after complete-coverage/capacity preflight, with guarded transmission and declared budgets; it never embeds documents, downloads a model, starts catch-up or hides a network call inside lexical lookup/fetch. Continuations, evidence-only calls and incomplete semantic coverage make zero embedding calls.

**Hosted embeddings send query text off the machine during semantic reads and document text off the machine during explicit embedding refresh.** They require explicit provider configuration, owner approval, consent and product privacy copy before use; lexical-only launch grants none of these. Local-provider selection remains subject to frozen §20 and explicit configuration. No hosted/local model, network or key operation is part of this authoring revision or the required lexical measurement protocol.

Maintenance embedding configuration and budgets are explicit and separate from reader work budgets. They constrain, rather than replace, the frozen process-wide identity ledger and local child ownership. Provide one shared coordinator across Worker isolates/handles, covering query and refresh attempts, money where applicable and active native children. Provider execution, estimation callbacks and child supervision also stay off the host main thread; the coordinator is an owned supervised service, not disposable request-Worker state. Worker restarts cannot reset totals, double-spend or duplicate local children. Reserve before transmission, revalidate the immutable request/service-grant binding and deadline after reservation under §4.1's two-sample model, retain unknown-usage charges, and keep active capacity reserved until actual underlying settlement/reaping. If that coordination is unavailable, refuse semantic configuration rather than advertising isolation with multiplied budgets. Follow §20's independent child supervisor and quarantine rules when the optional local model is selected.

## 7. WAL and lock policy — C-4

Support canonical DELETE and WAL databases and product sidecars in DELETE and WAL, including read-only context handles. Test all canonical/sidecar combinations; primary performance cells include DELETE/DELETE and WAL/WAL. A background maintainer may explicitly establish its sidecar's configured journal mode during initialization, with no concurrent product handles; it never switches a live canonical mode. Concurrent external journal-mode changes are outside the connection contract.

**Must qualify:** Linux ext4 on the production volume, private directory mode **0700**, canonical/sidecar/companion files **0600**. **Should qualify:** WSL2 ext4 and macOS APFS, reported separately; neither substitutes for the the production host result. Network filesystems are out of deployment scope. The read-only reader is explicitly permitted to let SQLite create owner-only WAL/SHM companions and read marks in the protected directory. Safe identity/permission checks still apply to existing and newly created companions. Production remains **DELETE**; WAL rollout awaits the owner after the product's re-run on `546d57ac`, and P2 does not perform that switch.

Reuse `topicJournalMode`, `createTopicSqlitePolicy`, native diagnostics and the Worker dispatch policy; generalize their use rather than adding another sleep/retry subsystem. Detect each database from the complete safe 100-byte format-3 header, verified descriptor/device/inode, before lock-taking metadata PRAGMAs. Only 2/2 enables WAL waiting. Unknown/truncated headers retain zero wait and normal layout refusal. Install the policy **before the first configuration/validation statement**, including `application_id`/`user_version`, to cover E1-C2's first-statement race.

Use one operation-wide native WAL wait window of **100 ms**, capped by remaining monotonic request/maintenance deadline. Canonical and sidecar connections share its start and end; do not restart it per connection, transaction or statement. Query work consumes this window. Refresh floored nonnegative remaining time before prepare, cached execution, iterator step, BEGIN/COMMIT/ROLLBACK, including zero after expiry. DELETE connections retain zero wait. Additionally retain E1-C2's **five fixed 30 s windows** per registered contention cell plus paired no-reader writer baseline, reversing pair order on odd repetitions. These fixed-window controls and the success-count latency series are separate populations; meeting one never substitutes for the other. Do not lengthen a fixed window after seeing its overlap count.

| Registered cell class | Required public-write overlap / native commits / close overlap |
| --- | --- |
| Fresh per-request writer reader-load | Per 30 s window: ≥20 reader attempts overlapping actual public-write calls, ≥100 successful native commits inside those calls/window, **≥10 attempts overlapping fresh per-write close**. Also satisfy per-request overlap/success minima in the separate latency series. |
| Retained-writer reader-load control | Per window: ≥20 attempts overlapping actual public-write calls and ≥100 in-call/in-window native commits. **No fresh-close minimum**; final retained shutdown close is reported separately and cannot qualify as per-write close. |
| Paired no-reader writer baseline | ≥100 successful native public-write commits per window; no reader/write-overlap or close-overlap minimum because there are no readers. Record the same writer lifecycle/deadlines. |
| Idle latency/cold or quiescent functional series | No contention-exposure minima. Apply its success minimum and all applicable loop/latency/bytes/functional gates. |
| Deliberate lock-exhaustion, abort or crash series | Assert its pre-registered expected outcome; report overlap/diagnostic completeness. Never include these injected-failure samples as a zero-busy/normal-latency pass. |

Below an applicable exposure minimum makes that fixed-window cell **invalid**, never pass. Baseline commits exclude opener/fixture commits, sleeps and retained shutdown close. Successful latency samples lacking their required overlap remain insufficient even if a separate window has ample commits.

### 10.4 Freshness and availability gates

Pre-register a continuous-writer workload and the explicit cron-renewed pump settings. After the **first completed certified build** of both required intents, count **all scheduled normal index-dependent `findCandidates` and `contextRead` attempts** in the fixed owner/readSet/type/intent cell. The denominator includes errors, timeouts, stale/unavailable results and fallback invocations; exact evidence-only calls are not allowed to dilute it. No exclusion of maintenance/dirty/cron-gap intervals after the initial build. Report all-attempt error categories separately. Require at least **100 index-dependent attempts per availability cell** across its registered windows; otherwise inconclusive.

**Not-ready fraction ≤1%** is `(index_unavailable + failures explicitly caused by stale/unvalidated/incomplete index state) / all scheduled normal index-dependent attempts`, with mutually exclusive per-attempt classification; timeouts/other errors are reported and remain subject to their independent gates. Fallback success is still a not-ready engine attempt. Overflow due solely to deliberate namespace selection is a separate scope-partial condition, not index-not-ready; report it and do not mix it into four-namespace launch coverage.

**New Memory or Card searchable within 30 s p95 under continuous writes:** record the canonical commit at which each synthetic item first becomes eligible for the tested intent (for current Cards, confirmed and eligible). Use pre-registered unique lexical probes whose expected top-24 membership is known from canonical fixture contents, and probe from fresh authorized handles at ≤1 s intervals, without repair/catch-up in a probe. Latency is from eligible canonical commit to the **first successful engine search containing the exact new ref/revision**, including cron wait, scheduling, build/catch-up and probe delay. Fallback is not searchable evidence. Keep continuous writers running until at least 30 s after the final eligible commit; register a bounded final observation/drain ceiling before the run. Items never observed by that ceiling are right-censored, retained as +infinity for the gate quantile, not deleted from the population. Report counts, finite/max and censored delays by type/intent/size/mode; require **≥100 eligible committed targets per applicable type/intent cell** or mark inconclusive. v18 has Memory targets only; mixed launch cells require both types. The nearest-rank p95 must be ≤30 s in every applicable cell.

Strict fresh-fence semantics may expose insufficient maintenance capacity under sustained writes. These gates are requirements, **not measured feasibility claims**; a failing implementation must improve background scheduling/index architecture within this contract or return for explicit contract review, not serve stale/partial-built lexical indexes or relax the targets. Partial namespace overflow remains distinct from index freshness.

A 2 s single-repetition smoke validates harness operation only. A failed, invalid, inconclusive or missing required production/platform cell prevents a blanket pass. Preserve raw attempt/telemetry records and actual process exits; report failure and recovery options without automatically restarting an expensive run.
