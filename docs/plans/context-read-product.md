## 1. Purpose, evidence and compatibility boundary

The commercial product wants its ChatGPT `ask_cairn` tool and website search to retrieve Memories and Cards together through `find_memory_candidates`, `fetch_memory_candidate_evidence` and `read_memory_context`. Its private repository is unavailable to this author. The following observations are **product-supplied evidence from a synthetic trial against `b2513501`, Node 24**, not measurements reproduced here:

| Product observation | Consequence for this proposal |
| --- | --- |
| 1,112 Memories across four namespaces; memory-only v18 reads preserved user_version, logical hash and file hash, and the old pin reopened the file. Cards required v23. | Preserve production v18 without canonical migration; distinguish capabilities by physical schema. |
| 52 handwritten Chinese questions, lexical only: recall@5 and recall@12 reported as 92%. | Directional evidence only. Freeze queries and relevance labels before a new recall comparison; Japanese and mixed queries still need coverage. |
| A four-namespace readSet failed `invalid_read_set`; four separate calls summed to 1.36 s at 1,112 Memories and 4.47 s at 3,336. | One authorized projection and one engine ranking must replace product-side fan-out. |
| Initial lexical build took 4.5 s at 1,112 Memories and returned `index_unavailable` at 3,336. | Request success must not depend on finishing index construction in that request. |
| A 50 ms deadline still allowed 0.31–1.06 s loop gaps; every request exceeded the 100 ms main-loop budget. | Isolate native work and counting in a Worker; add a parent-controlled response cutoff. |

Production remains **schema v18**. P2 introduces no canonical migration, DDL, index, trigger, capture hook or writer callback. An explicitly authorized sidecar maintainer is sufficient for memory-only production use. Upgrading canonical storage to enable Cards is a separate product rollout, never a side effect of opening a reader.

Product decisions now fix the deployment posture: **fresh open → read → await close per HTTP request**, including cold runs in the ≤100 ms host-loop maximum; lexical-only default; personal plus at most 31 selected projects; supervised maintenance of the owner-wide Memory+Card `current` and `history` projections. New items must become searchable within 30 s p95 under continuous writes, with ≤1% not-ready requests after initial build. Not-ready lookup falls back in the product to today's Card search plus `recall_memory`, marks coverage partial and adds no user-facing copy. Engine refusal remains truthful and never starts fallback, catch-up or inference itself. Exact latency gates are in §10.

The frozen baseline is [unified-memory-v1-contract.md](unified-memory-v1-contract.md): U5a §13, U2c §14, U5b §§15.1–15.7, the superseding §15.8 representation amendment, and §§17–§20. In particular, §15.8 supersedes earlier §15 DTO examples (`docs/plans/unified-memory-v1-contract.md:1439`, `docs/plans/unified-memory-v1-contract.md:1473`, `docs/plans/unified-memory-v1-contract.md:1608`). No frozen section is edited by this packet.

Only the new product profile changes four execution rules: Worker execution/hard response deadlines (C-1), the readSet bound (C-2), request-time maintenance (C-3), and WAL eligibility/lock handling (C-4). These are explicit opt-in amendments to §13.1, §13.2, §13.4 and §15.1, including §19.4's allowance for final work after a cooperative deadline. Every other evidence, authorization, accounting, currentness and representation rule remains authoritative.

## 3. Version identity and unchanged defaults

Select P2 through **new constructors** with literal `profile:'context-read-product-v1'`; retain `version:'context-read-v1'` for the existing data contract. Unknown/missing product profile on these constructors refuses `invalid_input`. Existing `openContextReader`, context-enabled `openMemoryCore`, `openMemoryReader`, tools and CLI defaults do not silently switch execution modes or widen validation.

Without P2 selection, preserve byte-identical DTOs, ordering, errors, capabilities, tool descriptions/schemas, prompts and provider-call counts. No new default field, background timer, Worker, sidecar probe, environment lookup or network call is introduced in legacy paths. Compatibility golden comparisons normalize only pre-existing nondeterministic fields explicitly identified by the test; metered serializer bytes and tool-list bytes are exact.

Product capabilities additionally identify the profile, execution mode, hard response cutoff, cancellation support, readSet maximum, deterministic namespace-selection policy, ready-only index use, supported schema/type combinations and journal support. Candidate/evidence/assembly success DTOs retain U5a/U5b shapes; namespace truncation uses existing coverage/trace containers as specified in §5. Lifecycle status is a separate host API, not a field inserted into the metered representation. The default product profile is lexical-only, with no embedder constructed or selected implicitly.

Use a separate product sidecar suffix, **`.context-read-product-v1.sqlite`**, with independently versioned format 1 and a product-profile marker. This avoids making legacy readers refuse their own cache after product maintenance enables WAL, and avoids mutating old generations in place. No implicit import, conversion, deletion or repair of `.context-read-v1.sqlite`. Product initial construction is an explicitly scheduled build, even if a legacy sidecar exists. Reuse the storage algorithms and invariants, not legacy file ownership.

Bind product cursors/snapshots to the product profile and canonical readSet in addition to all existing bindings; they are opaque strings with the same bounds. Reject cross-profile cursor/snapshot reuse as `invalid_cursor`/`invalid_snapshot`. Compact item fences retain the existing store-local `snapshot-item` HMAC and eight-character prefix; this profile does not replace that identity or mint new authority.

## 4. Public API and execution boundary — C-1

Proposed core exports (names are part of this draft):

```js
const supervisor = createContextReadSupervisor(); // owned before any async open
const reader = await openContextProductReader({
  supervisor,
  path,
  version: 'context-read-v1',
  profile: 'context-read-product-v1',
  readSet,                         // host-fixed, canonicalized once
  ownerCoverage,                  // trusted selection descriptor, §5
  host: { moduleUrl, configuration },
  diagnostics: false,              // literal true opts into native diagnostics
  deadlineMs: 5000                 // opening deadline; 1..5000
});

await reader.getContextReadCapabilities();
await reader.getContextIndexStatus({ readSet, types, intent, deadlineMs }, token, { signal });
await reader.findCandidates(input, token, { signal });
await reader.contextRead(input, token, { signal });
await reader.fetchCandidateEvidence({ ...fetchInput, deadlineMs }, token, { signal });
await reader.close();
// HTTP finally closes a returned handle; service shutdown always also does:
await supervisor.close();          // includes failed-opening resources
```

All methods return Promises of envelopes, including fetch and capabilities. Constructor option validation rejects invalid input before dispatch; operational opening failures reject with a sanitized coded error and opaque `cleanupId` owned by the supplied supervisor. No partially initialized reader escapes. Reader `close()` is idempotent, stops dispatch and awaits actual Worker/native cleanup; successful request lifecycle latency includes that awaited close. Failed-opening resources remain observable through the supervisor even though no reader was returned (§4.4).

`input` and `fetchInput` retain existing strict core grammars and bounds. Query/fetch/status deadlines are positive integers 1–5,000 ms, default 1,000 ms. Fetch gains `deadlineMs` **only on this profile**; it supports existing full refs, aligned internal fences, or snapshot, with their original mutual exclusions. The product tool adapter accepts compact refs under §15.8 and expands them against the immutable startup mapping. The adapter must await fetch and propagate disconnect/abort through the separate `signal` control argument. Signals, tokens and host configuration never become model-supplied tool fields. The P2-only fetch tool schema may expose bounded `deadlineMs`; legacy schemas stay exact.

The trusted host fixes the readSet. Core requests repeat it, accepting permutations that normalize to the fixed set; omission or a different well-formed set refuses `invalid_read_set`. A new selection requires a new handle and mapping, never live reordering of compact `ns` indices. MCP and website adapters inject that fixed set; an LLM cannot supply namespaces, authority, fences, bootstrap modules, maintenance options, providers or ranking configuration.

### 4.1 Non-transferable host functions

`host.moduleUrl` is a trusted constructor-only local file module, loaded **inside the fixed Cairn Worker entry**, exporting `createContextReadHost(configuration)`. It supplies the existing synchronous `{authorize,isCurrent}`, optional exact `{id,countTokens}`, and explicitly configured optional embedder/policy/local-status ports. It does not open a migration-capable core. Configuration and per-call tokens must be bounded structured-cloneable data; closures, function-source evaluation and serialized grants are unsupported. The host authenticates and issues its own opaque tokens; cloning a token is never an authorization decision.

The module is explicit host code with host privileges, never a URL or import selected by request data. No network module loading, environment-inherited provider selection, model download or key discovery occurs implicitly. An absent counter still permits candidates/fetch and refuses assembly under the existing counter contract.

The Worker-local authority must synchronously consult the host's request authority and an engine-verifiable authority lease registry. The product binds owner, namespaces and writer/erasure-fence generation at request start; that snapshot is the expected authority vector, not proof that it is still admissible at final reading. A stale allowlist or parent-provided `authorized:true` is insufficient. Construction refuses `authority_required` if the bootstrap cannot supply the lease seam below. Do not fall back to main-thread SQLite or a parent RPC after final reading. The current MCP WeakMap authority therefore needs an explicit product adapter, not a generic function copier.

Authorize the complete method/input, including fetch fences and every namespace, before index access or transmission. Recheck after every await, before provider transmission, publication and final validation. No host callback, counter or await occurs in a transaction or after the final authoritative read. The Worker posts the already frozen result synchronously after that read; parent IPC delivery is transport, not a later revalidation point. Linearization remains the Worker's final canonical snapshot acquisition, protected through transaction completion by the lease below. Subsequent canonical mutations retain frozen snapshot/ref semantics.

#### 4.1.1 Final-read authority lease (audit F1)

The host supplies one coherent registry for its authority realm, shared across reader Workers and all revokers/erasure-fence publishers. Each owner and namespace has a positive effective generation, a pending-revocation bit and active lease holders. Lease acquisition is a **single atomic decision over the owner plus every selected namespace generation**, not successive independent checks. An implementation may use a short serialized registry operation or an equivalent atomic protocol; it must never wait on the host main loop. Failure to establish a coherent vector before the deadline fails closed, initially `authority_required`, or `scope_changed` after a grant. No lease may be synthesized from a copied request token alone.

1. Immediately before opening the final canonical transaction, run the last synchronous `isCurrent` callbacks outside transactions. Then synchronously acquire the engine lease against the exact expected owner/namespace generation vector, normalized readSet, request/payload binding, operation ID and supervisor epoch. Acquisition atomically rejects mismatched generations or any pending revocation. A callback result followed by a separate unprotected BEGIN is forbidden.
2. Hold the lease continuously across deferred BEGIN, **the first read that acquires the SQLite snapshot**, every admitted-item/fence comparison, and COMMIT/ROLLBACK. No provider, host callback, counter or await occurs inside this interval. An empty-result claim and final candidate delivery also require their final canonical/index freshness checks under this protection. Maintenance publication uses the same authority protection across its final checks and sidecar publication commit.
3. A revoker atomically installs the next-generation vector and marks the affected owner/namespace set pending, prohibiting new leases. If no intersecting leases exist it publishes that vector immediately; otherwise the last intersecting lease's core-owned release atomically publishes the pending vector. A multi-namespace revocation becomes effective as one vector, not entry by entry. **Revocation becomes effective at that generation publication**, not when requested or merely marked pending. Existing final-read leases may finish as one in-flight request; later acquisitions fail closed. Thus a revocation requested between the last callback and snapshot acquisition either wins before lease acquisition (`scope_changed`, no success), or is deferred behind an already acquired lease and becomes effective after the read completes. It cannot become effective in the protected interval.
4. Release is a core-owned atomic registry operation in `finally`, after transaction completion/disposal, **not a host callback**. No host callback follows final reading. On timeout/cancel/crash, public settlement does not release the lease: the supervisor releases an orphan only after observing native/Worker termination and transaction disposal. An expiry timestamp or timer alone cannot authorize release. Unconfirmed termination quarantines the lease/realm entries and prevents an unsafe replacement; it cannot silently make revocation effective.
5. The lease gates authority changes only. It does not reserve a SQLite writer, hold a canonical write lock, or delay ordinary capture/review commits. Actual content/erasure mutations remain canonically fenced; the host must document how its erasure generation and effective authority advance follow this ordering. Cross-process revokers must participate in the same protocol; if the host cannot synchronize them, it cannot advertise this seam as implemented.

This chooses the product's **one-request revocation granularity** with a precisely bounded protected phase, rather than promising immediate mid-request revocation. Record pending-to-effective delay and native cleanup lag. A worker blocked in native code may delay authority revocation until cleanup; that must not hold the ordinary writer beyond the existing SQLite busy/deadline bounds. The product must verify this protocol against its own fence implementation before P2a coding.

### Authority seam checklist for the product

The product verifies this exact numbered checklist against its private authority, policy and writer-fence code. That code has not been inspected here. A written pass/mapping for each item is a **P2a implementation prerequisite**, not a new runtime consent prompt.

1. **Owner binding:** authenticate server-side before open; bind one owner and authority realm to the HTTP request, bootstrap, token and every namespace. User/tool text cannot select or replace them.
2. **Namespace set:** enumerate only allowed namespaces server-side; apply §5's deterministic selection to that authorized list; freeze the selected canonical readSet and `ownerCoverage` per fresh handle. Compact `ns` expansion uses exactly that mapping. No cross-owner fallback or silent omission is permitted.
3. **Generation/fence:** provide a positive owner generation and one positive generation per selected namespace from the writer/erasure fence, plus a non-reused restore/realm epoch. Distinguish authority/erasure generations from ordinary content epochs: a capture commit is not implicitly an authority revocation. Bind the entire vector and complete method/payload, including fences and selection descriptor.
4. **Lease synchronization:** map registry acquisition, pending marking, effective generation advance and core-owned release to §4.1.1. All revokers, including other processes, participate. Prove atomic acquisition over the full vector; a request-start snapshot and separate atomic generation loads alone do not qualify.
5. **Revocation timing:** document that a denied/pending/mismatched initial request fails `authority_required`, a previously granted operation that cannot acquire its final lease fails `scope_changed`, and a revocation after acquisition becomes effective only after release. Include the rendezvous between the last callback and SQLite snapshot acquisition; do not claim immediate revocation during the lease.
6. **Synchronous seam:** `authorize`, `isCurrent` and final lease acquisition are synchronous in the Worker and outside transactions, with no network/parent RPC. Core atomic release requires no host callback. Counter/embedding callbacks and all awaits finish before the final protected read. Unknown/throwing/unverifiable authority fails closed.
7. **Transfer/token bounds:** tokens are own-data, cloneable request credentials, not grants/functions; maximum **16,384 UTF-8 bytes**, depth 16 and 8,192 nodes, within the 262,144-byte IPC cap. Bind request identity, owner/readSet, generations, expiry and method/payload; reject malformed/over-limit token as `invalid_input`, invalid credentials as `authority_required`. Neither tokens nor lease records enter model text, logs or public diagnostics.
8. **Cleanup/failure ownership:** supply the supervisor before open; failed bootstrap/open/timeout is still owned. Do not release orphan leases, writer-fence capacity or provider slots until native termination/disposal is confirmed. Preserve `read_timeout`, `read_cancelled`, `reader_failed` and `store_closed` precedence; do not turn failed authority into empty/partial authorized data.
9. **Request and restore lifecycle:** fresh open/read/await-close for each HTTP request; disconnect aborts the public call. Shutdown awaits supervisor cleanup, including constructors that rejected. Restore creates a new authority realm epoch so generations/tokens cannot be reused from before restore. Product fallback reauthorizes through its existing paths and does not confer authority on the engine's behalf.

### 4.2 Worker ownership and bounds

Reuse/refactor `memory-reader.mjs` dispatch, identity, resource, error, idle and termination machinery behind the new entry; preserve legacy behavior. SQLite-reaching imports remain dynamic behind the established local/CLI boundary, with no `createRequire` escape. Keep the Worker entry fixed, env empty, execArgv empty and output drained. All native open/configure/schema work, canonical/index reads, scoring, tokenization and exact counting run off the host thread.

One in-flight operation per handle, no implicit queue; overlap refuses `read_in_progress`. The reader and maintainer have distinct Workers, so background work cannot occupy the request slot. Retain bounded ranking state, 128 rankings/five-minute TTL and 60 s idle disposal; idle/crash/timeout invalidates retained cursors as `cursor_stale`. A valid durable snapshot can still be canonically refetched after reopening, subject to its fences and profile.

Parent validation inspects own data without executing getters/proxies and caps request/configuration IPC at 262,144 UTF-8 bytes per message; tokens have the stricter §4.1 checklist bound. Data responses still fit the existing 65,536-byte envelope, snapshots 16,384 characters, cursors 8,192 characters and tool transport 262,144 bytes. Reject oversized indivisible data as `context_item_too_large`. Clone/serialization costs and startup/settlement callbacks count toward the host-loop gate; offloading SQLite alone is insufficient. Select Worker heap limits explicitly after auditing the existing 128 MiB vector-cache allowance and counter runtime; do not copy the topic reader's 64 MiB heap blindly.

### 4.3 Hard response deadlines and cancellation

Measure one absolute monotonic deadline from public method entry, including bounded validation, IPC, any lazy restart/opening, authority checks, native waits, scoring, counter work and final canonical revalidation. The parent watchdog owns this deadline independently of Worker progress. Cooperative checks remain useful inside the Worker but do not define the public cutoff.

On expiry, latch `read_timeout`, discard all later **retrieval results** for that operation/Worker epoch, signal cancellation and request termination. Keep the independent native telemetry channel alive through cleanup (§4.5). **Settle the public call before awaiting termination, no later than deadline + 50 ms.** On AbortSignal, do the same with `read_cancelled`, settling within 50 ms of host-observed abort; pre-aborted calls dispatch nothing. On explicit close, settle active work with `store_closed`, then await cleanup. First terminal event wins; a result received at or after the absolute deadline is a timeout even if the Worker computed it earlier. A result accepted before the cutoff must have completed all frozen final checks. Opening deadlines use the same +50 ms public-rejection gate.

Never deliver a partially refetched evidence list or an assembly whose final validation was cut short. If an ordinary semantic timeout degrades to lexical and a fully validated result arrives before the outer cutoff, retain that frozen channel behavior. Otherwise the entire operation times out. Optional admission may stop early, but required metering/final validation must fit the hard response window or the result is discarded. Do not extend a deadline for a final pass.

“Hard” means a parent-enforced response cutoff and bounded public cancellation independent of native cleanup; it does **not** claim that Node terminates an executing SQLite step at an exact CPU instant. Timers also depend on host scheduling; the ≤50 ms overshoot is nevertheless an acceptance gate, not waived by that caveat. Record settlement overshoot and native cleanup lag separately. Keep resources quarantined until observed termination and provider cleanup settle; do not launch unsafe replacements or free capacity on a timer alone. Reader close and the supervisor's shutdown drain expose actual cleanup, including failed constructors.

### 4.4 Supervisor owns opening failures (audit F3)

`createContextReadSupervisor()` synchronously creates a SQLite-free resource owner before any constructor dispatch. Every product reader/maintainer constructor requires `supervisor`; registration of an operation ID, telemetry buffer, termination promise and cleanup ID happens **before** Worker creation/bootstrap. Every acquired native handle, authority lease and optional provider child joins that ownership record immediately, not only after construction succeeds. Constructors accept `{signal}` as their second control argument. Invalid option validation creates no Worker; bootstrap/open timeout and partial resource acquisition enter the same supervised cleanup path as a timed-out read.

The supervisor exposes these host-only operations:

```js
supervisor.getCleanupStatus(cleanupId); // synchronous frozen metadata, no paths
await supervisor.drain(cleanupId);     // await this failed/open/read cleanup only
await supervisor.drain();              // snapshot and await current cleanup records
await supervisor.close();              // stop new opens, cancel, then drain all
```

Cleanup status is exactly `{cleanupId,state,workerStopped,nativeDisposed,leasesReleased,providersSettled,telemetry}`, where `state` is `pending|complete|failed`, each disposal field is boolean (true also for a resource never acquired), and `telemetry` is `disabled|pending|complete|incomplete` (§4.5); disabled means diagnostics were not selected. Complete requires all disposal booleans true; diagnostic incompleteness is separate and never a zero-busy pass. Unknown cleanup ID refuses `invalid_input`. Metadata is bounded and contains no native message, path, owner or token. Opening rejection exposes only the coded error and its cleanup ID; operational failures cannot orphan an invisible Worker. `drain(cleanupId)` waits for that record only; argument-free drain snapshots records already entering cleanup and does not cancel/wait for unrelated healthy HTTP handles or the live pump. `close()` stops all resources owned by that supervisor and drains them. Failure to confirm disposal reports `reader_failed`, never completion from a kill request alone.

All supervisors participate in **one process-wide registry**, with fixed global resource limits, not per-request isolated quotas. Register a normalized path/profile/authority-realm key before open, then bind it to validated canonical device/inode identity; aliases of an already identified file share the quarantine. A pending failed-opening/terminated-operation cleanup blocks replacement opens for that store/realm with `read_in_progress`, even through a newly created supervisor. Unconfirmed failed cleanup latches `reader_failed` for that identity until explicit operator recovery after actual resource disposal; creating another supervisor/handle is not recovery. Healthy independent request handles may coexist within the process-wide limits; the quarantine is not a permanent one-reader-per-store lock.

Service shutdown must close the supervisor even if the HTTP constructor rejected and no handle exists. Its owned termination handlers retain live supervision until cleanup completes/fails; no detached PID/log constitutes supervision. Request settlement and shutdown drain are separate promises: the former meets +50 ms, while the latter awaits native cleanup off the host thread. After a bootstrap failure following resource acquisition, release only confirmed-disposed resources. No ordinary SQLite writer is gated by this registry; monitor any native read-lock lag against existing writer busy/operation bounds.

### 4.5 Native telemetry independent of result delivery (audit F5)

When diagnostics are selected, create a parent-owned, bounded shared telemetry buffer **before opening** and attach it to the supervisor operation. It survives discarded retrieval messages, constructor rejection and Worker termination. Native wrappers synchronously record a begin marker before each native open/prepare/execute/iterator/transaction/close call and an outcome marker immediately on return/throw, **before** public error mapping or `postMessage`. Every failure records only fixed stage/statement labels, numeric primary/extended SQLite codes and a monotonic event sequence. Never include SQL, native messages, paths, content, owner/namespace/entity IDs or tokens. Retrieval and telemetry have separate acceptance paths; a late retrieval result is still discarded.

Use atomic committed counters for total calls begun/completed, failures, native primary 5 and 6, in-flight native calls and overflow/lost outcomes; retain the corresponding sanitized failure records in a bounded ring. Each outcome publishes atomically after its record is committed. The parent never infers zero from an empty message queue. Telemetry tags bind operation ID, Worker epoch and diagnostic-protocol version; malformed/mismatched frames fail diagnostic completeness. Counter overflow or missing ring records is explicitly incomplete, not sampling. The implementation fixes/advertises buffer capacity before measurements and cannot grow it after seeing failures.

The supervisor drains after Worker/native/provider shutdown, reading committed shared state even if no result envelope arrived. Coverage is `complete` only when every begun native call has a committed outcome, no native call remains in flight, all records through the final committed sequence are present, no overflow/loss occurred, and termination is confirmed. Termination during an unreturned native call, a crash inside recording, or a missing diagnostic acknowledgement makes coverage `incomplete`; known busy events still count, but the cell cannot claim zero. A `BUSY` recorded just before the response cutoff therefore survives the subsequent `read_timeout`; if termination prevents observing the native outcome, the cell is **invalid** rather than zero-busy. Cleanup itself may be complete while diagnostic coverage is incomplete.

This telemetry is host/operator metadata, never a model text block or new evidence field. Measurement uses the union of public errors and retained native failures, with de-duplication by operation/event sequence; incomplete diagnostic coverage prevents acceptance even if all public responses were fast. Production diagnostics remain opt-in and legacy paths remain byte-identical.

## 5. Owner-wide readSet and deterministic fusion — C-2

The shape stays an array of full namespaces:

```js
[
  { ownerId, scope: 'personal', projectId: null },
  { ownerId, scope: 'project', projectId: 'project-a' },
  { ownerId, scope: 'project', projectId: 'project-b' },
  { ownerId, scope: 'project', projectId: 'project-c' }
]
```

Engine maximum: **32 distinct selected namespaces**, one owner, at most one personal namespace and **at most 31 projects**. A nonempty project-only subset or personal-only set is legal. Every namespace uses existing identifier/namespace rules. Reject duplicate, mixed-owner, malformed, sparse, accessor/unknown-field or oversized **selected readSet** input as `invalid_read_set` before sidecar work. An owner with more projects is supported by the deterministic partial-selection contract below, not by silently truncating an oversized engine request. “Owner-wide” means the host's authorized enumeration, not automatic discovery or permission to read every project belonging to an owner.

**Overflow selection policy `recent-projects-v1`:** the host derives the authorized project inventory from its own metadata, retains personal if it is in the requested authorized inventory, and chooses at most 31 projects by descending `lastActiveAt` (integer UTC epoch milliseconds; missing is 0). Ties use ascending UTF-8 project ID bytes. Activity is host project metadata, never inferred by request-time content/index scans; the selection revision freezes that inventory/activity snapshot for the request and matching maintenance projection. Compute/cache this ordering off the host main thread or use a bounded indexed metadata selection; do not synchronously sort an unbounded heavy-owner inventory in an HTTP callback. Selection is independent of query, incoming enumeration order and model output. No namespace priority/quota is applied inside the selected projection's ranking. Access filtering precedes selection; denied namespaces are not counted as omitted authorized projects.

The trusted constructor field is exactly `ownerCoverage:{policy:'recent-projects-v1',selectionRevision,requestedNamespaces,selectedNamespaces,omittedNamespaces}`. `selectionRevision` is a host-issued nonempty bounded identifier (≤200 UTF-16 units); counts are nonnegative safe integers, selected equals `readSet.length`, requested equals selected + omitted, and requested is at least one. When omitted is nonzero the selected list contains all requested personal scope (if any) plus the first 31 authorized projects under the frozen ordering; when zero no requested namespace is omitted. Authority request binding includes the descriptor/profile as immutable constructor configuration together with the complete existing method payload; it is not a new model-supplied input field. The host verifies selection against its inventory; the engine validates descriptor consistency and does not discover excluded projects or read their statistics. The engine request remains bounded even for a heavy owner's larger inventory.

If `omittedNamespaces>0`, candidate `coverage.status` and assembly `diagnostics.candidates.coverage.status` are **`partial`**, even when selected-projection lexical coverage is complete. Existing `trace` carries exactly `namespaceSelection:{...ownerCoverage}` (under `diagnostics.candidates.trace` in assembly); no new metered fields or full omitted-project list are added. Complete-empty for the selected set cannot claim complete-empty for the owner. Lifecycle coverage explicitly reports these same counts (§6.1). Exact evidence DTOs stay `{items,snapshot}`; product HTTP/tool metadata reports the same selection descriptor/partial status outside model text, never rewrites identities or claims an exhaustive owner result. The product does not perform namespace RRF.

Product overflow behavior is therefore deterministic partial coverage, not an error or an unannounced drop. The raw selected readSet cap still protects the engine. A selection change opens a fresh mapping/handle and requires a maintained matching projection; if it is not ready, product fallback is partial. Prebuild active selections and record selection churn; overflow selection may not be used to evade the four-namespace full-coverage gates.

Canonicalize with the existing UTF-8 namespace-key ordering, preserving the current mapping for existing one/two-namespace inputs. Both facade and sidecar projection validation must use the new profile-aware validator. Access-generation vectors are sorted with their namespaces; sorting them independently is forbidden. No namespace may be dropped silently. Authorization refusal fails the entire call; no partial authorized subset is inferred.

The **ranking rule is pooled projection ranking**, extending today's engine rule, rather than adding a second RRF over namespaces:

1. Construct the exact authorized union for normalized `(readSet, types, intent)`. Use one complete eligible-projection N, total token length and term df. Score every matching document with frozen T1/BM25 constants. Sort descending score, then binary canonical `(owner,scope,project,type,id)` tuple. No per-namespace top-k truncation before this score/rank.
2. If explicitly enabled semantic preflight is complete over that entire union and within existing vector/resident-byte bounds, embed the query once and score the full authorized vector set. Sort cosine ties with the same tuple. Never dispatch one embedding per namespace or fuse incomplete semantic coverage.
3. Fuse the **global lexical and global semantic lists once**, using the existing family preset: local `rrf-k60-d12` or hosted `rrf-k10`. Score is `sum(weight / (k + oneBasedChannelRank))`; absent membership contributes zero. Sort fused score descending with the same canonical tuple tie-break; retain the existing 24-item horizon, default limit 12 and maximum 24. Disabled/degraded semantic preserves global BM25 order.
4. Freeze this single ranking for continuation; namespaces do not receive quotas, weights or a priority based on input order. Equal bodies remain separate typed identities. ReadSet permutations cannot change ranks, compact namespace indices, statistics, snapshots' scope binding or results.

This is the deterministic engine fusion across namespaces: one pooled lexical/semantic universe followed by the established channel fusion. The product performs no RRF, score normalization or merging of namespace responses. P2 adds no new tokenizer, substring fallback or quality claim. Explicitly test the frozen one-character Han known miss separately from regression failures.

The initial product profile exposes baseline Memory/Card lexical retrieval, with semantic disabled and owner approval pending; the optional configured semantic seam retains its frozen semantics when explicitly enabled later. Optional relations/MOC, role reads, assets and Raw search are not enabled by P2. Source/profile requests unavailable on the product handle refuse `invalid_input`; legacy separately opted-in paths remain unchanged. Card current-dependency checks on schemas that contain them remain mandatory even without optional retrieval sources; background maintenance must observe their extra fences before statistics/publication, per frozen §19.4.

## 6. Index lifecycle and maintenance — C-3

### 6.1 Lifecycle and visibility

Readiness is **per exact normalized readSet/types/intent projection**, tokenizer/representation, store/profile identity and access/canonical/dependency fences. A ready single-namespace index does not imply a ready four-namespace index. The host pre-registers/builds projections it plans to query; unforeseen combinations return unavailable until explicitly maintained. Requests never manufacture aggregate statistics from incomplete shards.

`getContextIndexStatus` is an authorized, Worker-backed observation only, with the same hard deadline and fixed readSet. Its strict input is `{readSet,types,intent,deadlineMs?}`. Authority explicitly allowlists this method and binds the full input before any projection observation. Its success envelope has **exactly** this host-only DTO; all displayed fields are present, no additional keys, and this is not model text:

```text
{profile:'context-read-product-v1',
 lexical:{state,reason,progress},
 semantic:{state,reason},
 coverage:{status,freshness,byType,namespaces}}

progress = null | {phase,checkpoint,sequence,baseSequence}
byType = {memory?:{eligible,indexed,embedded}, card?:{eligible,indexed,embedded}}
namespaces = {policy:'recent-projects-v1',selectionRevision,
              requestedNamespaces,selectedNamespaces,omittedNamespaces}
```

`byType` has exactly the requested type keys in Memory/Card order, never unsupported types. Every count is null or a nonnegative safe integer. Progress phase/checkpoint/baseSequence are nonnegative safe integers, sequence is positive, and `baseSequence<=sequence`. Progress is the latest **validated durable checkpoint**, not speculative in-flight work; phase is the completed scan-stream count or current stream ordinal under the format's fixed stream order. Namespace fields equal the constructor descriptor. Lifecycle lexical `state` is exactly `absent|building|ready|stale|catching_up|unavailable`; no liveness is inferred from it.

| Lexical state | Exact reason / progress | Exact coverage and counts | Request behavior |
| --- | --- | --- | --- |
| `absent` | `reason:'missing'`; progress null. No generation/checkpoint exists for the projection. | `status:'unavailable',freshness:'unverified'`; all type counts null. | `index_unavailable`, no create/build. |
| `building` | `reason:'initial_build'` or `'rebuild'` from the checkpoint's fixed build kind; progress nonnull, baseSequence 0. | `unavailable/unverified`; all type counts null. | Incomplete first/rebuild work is not searchable. |
| `ready` | reason null; progress nonnull, matching certified publication. | `status:'complete'` iff omittedNamespaces is 0, otherwise `'partial'`; freshness `'current'`. Eligible/indexed from the validated record and equal; embedded follows semantic rules below. | Search selected projection; whole-owner coverage remains partial on overflow. |
| `stale` | No valid resumable delta checkpoint for the current fences. Unsafe canonical files keep existing opener errors instead of this DTO. |

Coverage status is exactly `complete|partial|unavailable`; freshness exactly `current|stale|unverified`. Missing checkpoint alone means absent; missing validation evidence on an apparently published generation means unavailable/validation_missing. Invalid HMAC/bindings mean validation_invalid; an observed native corruption signal means corrupt. If a checkpoint's target access/canonical/dependency vector no longer matches, classify stale rather than resumable. File/format identity failures take unavailable precedence over stale. A read handle closed/discarded returns `store_closed`, with **no success DTO**, not a synthetic closed-state status.

Semantic lifecycle is exactly `{state:'disabled',reason:'not_enabled'}` for the default product profile, even if a provider is merely configured; every embedded count is null. On an explicitly enabled semantic profile, use `{state:'absent',reason:'not_configured'}` without a provider, `{state:'stale_index',reason:'index_not_ready'}` when lexical is not ready, `{state:'unavailable',reason:'provider_unavailable'}` for an unavailable selected provider, `{state:'partial_coverage',reason:'missing_vectors'}` for an otherwise ready incomplete vector publication, or `{state:'ready',reason:null}` for complete validated coverage. This listed order resolves simultaneous conditions. Embedded counts are known only from a matching certified vector manifest; otherwise null. Semantic lifecycle readiness does not authorize transmission or promise an attempted provider call.

These states describe durable work, not active execution: after a maintainer crashes or stops, valid initial progress remains `building` and valid delta progress remains `catching_up/resume_pending`, with unchanged checkpoint. A reader restart produces the same status from the same records/fences; no heartbeat or still-live PID is required. No read/status call persists a marker, renews a task or queues repair. Only an explicit refresh resumes work.

Incomplete lexical generations remain unavailable. Overflow partial coverage (§5) describes selected namespace scope and does **not** permit searching incomplete indexes. Lexical-ready/vector-incomplete reads with explicit `semantic:true` retain existing `partial_coverage` degradation and zero query embedding calls. Maintenance may return `partial`; neither partial nor unavailable is “no matches.”

#### 6.1.1 Published validation handoff (audit F2)

The product sidecar format adds immutable published lexical generations and a keyed `validation_records` table plus one projection publication pointer. The maintainer alone creates records after deep integrity/statistics/eligibility verification. A fresh/restarted reader must consume an already certified generation successfully **without another maintenance call** or deep scan. A certificate is evidence of cache validation, never authority to read canonical data.

One lexical validation record is a closed, canonical-JSON object, maximum 16,384 UTF-8 bytes:

```text
{version:'context-index-validation-v1',profile:'context-read-product-v1',format:1,
 storeId,canonical:{device,inode,applicationId,userVersion,schemaVersion},
 sidecar:{device,inode,incarnation,schemaVersion},
 projectionDigest,accessDigest,canonicalFenceDigest,dependencyFenceDigest,
 tokenizer,representation,
 generation:{id,sequence,checkpoint,incarnation},publicationId,manifestDigest,
 counts:{byType:{memory?:{eligible,indexed},card?:{eligible,indexed}},
         documents,terms,totalTokenLength},mac}
```

All IDs are nonempty ≤200-unit strings; generation IDs are opaque digests/identifiers rather than the entire serialized namespace array. Positive/nonnegative integers follow the status rules. Device/inode are canonical decimal strings from the safe descriptors. Digests and mac are full 43-character base64url HMAC/SHA-256 values, not compact fence prefixes. `projectionDigest` binds canonical selected readSet/types/intent and profile; activity selection provenance belongs to request coverage rather than lexical statistics identity. `accessDigest` binds the stable owner/namespace effective-generation vector and restore realm epoch, **not** a fresh request token/lease ID. Canonical/dependency digests cover all frozen required epoch/support/currentness fences. Manifest digest covers the maintainer's verified lexical document/postings/statistics manifest; counts agree with it. No body/source text, vectors or plaintext namespace list enters the record.

Compute `mac` over the canonical record without mac using the existing store-local secret in the distinct `context-read-product-v1/validation` HMAC domain. This is store-local integrity binding, not new provider key access. Table/format and canonical schema-version checks must be physically attested; device/inode checks bind open descriptors, not path strings. Platforms with a different stable file identity require an explicitly qualified equivalent and protocol revision; the launch gate uses Linux device/inode.

For these records, canonical JSON recursively sorts object keys by UTF-8 bytes, preserves canonical namespace/row-array order and emits exact safe integers; hash UTF-8 bytes with SHA-256, no implicit Unicode normalization. The lexical manifest streams the format-defined document tuples (typed canonical identity, revision/bodyRevision, eligibility, representation and token length), then posting tuples (same identity, term, frequency), then statistics tuples (term, df, N and total length), ordered by canonical identity and term bytes within each table. The maintainer verifies row joins/counts/statistics before hashing; a mere hash of unchecked tables is insufficient. The reader authenticates the recorded digest/bindings and does not re-stream tables.

Incomplete checkpoints have a separate closed record, ≤4,096 UTF-8 bytes: `{version:'context-index-progress-v1',profile,storeId,canonicalIdentityDigest,sidecarIdentityDigest,projectionDigest,accessDigest,canonicalFenceDigest,dependencyFenceDigest,generation:{id,incarnation},kind,progress,mac}`. Identity digests bind the same file/schema identities above; kind is exactly `initial|rebuild|delta`, progress has the exact §6.1 fields, and mac uses the distinct `context-read-product-v1/progress` domain. Commit it atomically with the corresponding durable batch/verification checkpoint. Status verifies this one keyed record before exposing progress; it never claims certified searchable counts from it. A missing/invalid record on apparent incomplete work is unavailable/validation_missing or validation_invalid, not fabricated progress. This provides durable crash/reopen status without a deep scan or liveness heartbeat.

Build/catch-up uses a separate staging generation. Published lexical documents/postings/statistics are immutable; background changes never mutate rows under a live lexical certificate. Deep validation can checkpoint bounded verification progress against an unchanged staging manifest. The final sidecar transaction atomically installs the complete generation, full validation record and projection pointer only after authority lease and canonical/dependency fence revalidation. A kill before commit leaves the previous pointer or an incomplete checkpoint; it cannot publish a ready flag without its certificate. Exactly one coordinated maintenance writer owns a projection; every structural/data update invalidates affected validation evidence or replaces it atomically. An independently certified vector manifest binds the same lexical publication and exact embedder identity; vector refresh cannot invalidate or rewrite unchanged lexical statistics under a certificate.

After per-call authorization, a reader performs only: safe descriptor/identity and scalar physical-format/schema checks; one keyed projection-pointer lookup; one keyed validation-record lookup; bounded decoding/HMAC/binding comparison; scalar canonical/access/dependency fence probes over ≤32 namespaces and existing declared-dependency bounds; and scalar comparison of pointer/generation/publication/checkpoint/incarnation. Read pointer/record/generation in the same sidecar read transaction and recheck publication/fences before final delivery. Counts come from the authenticated record, not request-time COUNT/postings/statistics scans. Reuse a valid record across fresh handles; no process-local warm certificate is required. Treat missing/mismatched record as honest unavailable.

Invalidators are explicit: canonical file/store/schema identity or restore epoch; sidecar file identity/incarnation/schema/format; selected projection/types/intent; effective access generation; tokenizer/representation; canonical/dependency fence; publication/checkpoint/generation pointer; invalid record MAC/manifest binding; or an observed native corruption signal. Changes unrelated to the projection do not invalidate it. Same-database DML is trusted only through the coordinated maintenance writer; arbitrary same-user edits/undetected bit rot are not certified by a one-row read. ### 10.4 Freshness and availability gates

Pre-register a continuous-writer workload and the explicit cron-renewed pump settings. After the **first completed certified build** of both required intents, count **all scheduled normal index-dependent `findCandidates` and `contextRead` attempts** in the fixed owner/readSet/type/intent cell. The denominator includes errors, timeouts, stale/unavailable results and fallback invocations; exact evidence-only calls are not allowed to dilute it. No exclusion of maintenance/dirty/cron-gap intervals after the initial build. Report all-attempt error categories separately. Require at least **100 index-dependent attempts per availability cell** across its registered windows; otherwise inconclusive.

**Not-ready fraction ≤1%** is `(index_unavailable + failures explicitly caused by stale/unvalidated/incomplete index state) / all scheduled normal index-dependent attempts`, with mutually exclusive per-attempt classification; timeouts/other errors are reported and remain subject to their independent gates. Fallback success is still a not-ready engine attempt. Overflow due solely to deliberate namespace selection is a separate scope-partial condition, not index-not-ready; report it and do not mix it into four-namespace launch coverage.

**New Memory or Card searchable within 30 s p95 under continuous writes:** record the canonical commit at which each synthetic item first becomes eligible for the tested intent (for current Cards, confirmed and eligible). Use pre-registered unique lexical probes whose expected top-24 membership is known from canonical fixture contents, and probe from fresh authorized handles at ≤1 s intervals, without repair/catch-up in a probe. Latency is from eligible canonical commit to the **first successful engine search containing the exact new ref/revision**, including cron wait, scheduling, build/catch-up and probe delay. Fallback is not searchable evidence. Keep continuous writers running until at least 30 s after the final eligible commit; register a bounded final observation/drain ceiling before the run. Items never observed by that ceiling are right-censored, retained as +infinity for the gate quantile, not deleted from the population. Report counts, finite/max and censored delays by type/intent/size/mode; require **≥100 eligible committed targets per applicable type/intent cell** or mark inconclusive. v18 has Memory targets only; mixed launch cells require both types. The nearest-rank p95 must be ≤30 s in every applicable cell.

Strict fresh-fence semantics may expose insufficient maintenance capacity under sustained writes. These gates are requirements, **not measured feasibility claims**; a failing implementation must improve background scheduling/index architecture within this contract or return for explicit contract review, not serve stale/partial-built lexical indexes or relax the targets. Partial namespace overflow remains distinct from index freshness.

A 2 s single-repetition smoke validates harness operation only. A failed, invalid, inconclusive or missing required production/platform cell prevents a blanket pass. Preserve raw attempt/telemetry records and actual process exits; report failure and recovery options without automatically restarting an expensive run.
