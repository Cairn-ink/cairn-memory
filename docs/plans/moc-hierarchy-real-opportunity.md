## Why ordinary capture did not activate the hierarchy

This is a topology-entry mismatch, not evidence of classifier incapability or
forced model blame. The [classifier instruction, lines 10–17](../../core/prompts/classify-placement.md)
explicitly permits standalone L1s and demonstrates that shape. The
[strict dynamic schema](../../adapters/openai/schemas.mjs#L402) also permits
optional `newL2Title`; the [wire decoder](../../adapters/openai/classification-wire.mjs#L34)
preserves it. [Placement](../../core/moc-storage.mjs#L157) creates an L2 only when
that optional field is present. In contrast, the
[private root catalog](../../core/moc-storage.mjs#L487) requires a live connected
L2, and [traversal](../../core/moc-recall-candidates.mjs#L122) discovers L1 only
under selected L2s. A valid filed standalone L1 is therefore not an entry.

A separate private synthetic harness first reproduced this with one ordinary
captured/classified memory, then cold H2 recall: one filed L1, zero roots/group
calls, exact flat fallback and unchanged receipts. Adding only optional
`newL2Title` through the same capture path created a connected L2 and activated
both group calls. Both controls also passed through the actual OpenAI adapter
with fake HTTP. Ordinary capture **can** create L2; the output shape that omits
it is also valid. Initial classification records a batch's attempt, not
navigable ancestry or semantic success; see [ADR0002](../adr/0002-attribute-initial-classification-to-capture-batch.md).

The private diagnostic was run with the repository's owned runner:

```text
node tools/testing/run.mjs --script <private-synthetic-harness> MODE
```

The red assertion describes desired behavior, not a broken existing H2 promise.
All stores were closed/removed before verdicts. This private harness is not

organization rather than inventing topics or ancestry.
