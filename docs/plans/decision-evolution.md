# Decision-evolution evaluation contract (first delivery)

This delivery freezes a small, synthetic, source-backed diagnostic before any core or MCP implementation. It does not measure product performance.

## Observable acceptance criteria

- DE1: A model-facing fixture contains only attributed meeting events and questions. It includes English and Traditional Chinese development and held-out cases. Evaluation expectations and relationship edges live only in a separate rubric; the harness never passes that rubric to an answer callback.
- DE2: Cases exercise an initial A choice on price/quality grounds, considering B, tentative B, explicit adoption of B replacing A, failure of a reason without a decision change, another actor choosing the same vendor in a separate scope, late ingestion of an older meeting, and a partial reason change. The expected state remains scoped to actor and decision and distinguishes considering, tentative, adopted, historical supersession, and needs-reconfirmation.
- DE3: The offline scorer checks evidence IDs, current state, rationale status, and directed explicit-supersession edges. It rejects absent/reversed edges, tentative-as-final, and cross-person attribution. It reports unknown/incomplete separately from wrong; it cannot prove that arbitrary text semantically entails a claim.
- DE4: Tests use deliberately bad responses as negative controls, including missing and reversed updates. They run without a model, credentials, database, or live MCP. A script exposes the check on supported Node runtimes.
- DE5: Documentation specifies a later, separately authorized, three-arm actual-core/MCP experiment: current MOC recall, linked decision context, and full source for a small bounded set. It specifies evidence recall, commitment/state accuracy, false-link rates, latency/tokens/cost, and incomplete/unknown accounting. No scripted score is reported as real-world accuracy.

## Boundaries and evaluation interpretation

Fixtures are synthetic and ordinary-language, not an authored graph fed to the answerer. A caller may use a genuine memory implementation later, but must keep the rubric out of ingestion, retrieval, prompts, and any answer callback. The offline scorer is a reproducible structural diagnostic only. Source-ID membership and edge orientation do not establish semantic entailment or model reasoning. For a real evaluation, freeze fixtures and rubric before scored runs and arrange independent semantic review of generated answers and cited source passages.

The `heldout` label means reserved from development prompts within this *public* diagnostic. Once inspected or tuned against, these cases are not an independent hidden test or benchmark. There is no hidden evaluator here. The fixture timestamps describe occurrence and ingestion for the harness; the current capture path does not accept them as trusted per-event chronology metadata. A later adapter must preserve timing as ordinary attributed source text or use an explicitly reviewed API, and report when timing cannot be carried faithfully. It must not manufacture chronology from ingestion order.

## Running and interpreting the offline diagnostic

Run `npm test` or `node --test evaluation/decision-evolution/test/*.test.mjs` on Node 22.16 or 24. `runDecisionEvolution({fixture, answer, split})` passes only `{caseId, language, events, question}` to the callback. The fixture validator rejects extra evaluator fields. The separate `scoreDecisionEvolution({fixture, rubric, run})` compares one structured response per question. A response is either `{status:'unknown'}`, `{status:'incomplete'}`, or `{status:'answered', state, evidence, nonFinal, reasons, updates}`. `state` has `{actor, choice, commitment, basis}`. `nonFinal` records `{choice, stage:'considering'|'tentative', evidence:[source IDs]}`; `reasons` records `{label, status:'active'|'challenged', evidence:[source IDs]}`. `updates` uses `{from:newDecisionSourceId, to:oldDecisionSourceId, type:'supersedes'}`. This edge direction is replacement **supersedes** predecessor, not older-to-newer chronology. A later-ingested older minute is not an update. A challenged premise without adoption of a replacement is not an update.

Canonical choice and reason labels are evaluator annotations. Real free-form answers need a frozen, answer-blind normalization protocol or independent annotators before this diagnostic can score them. Supplying per-case expected labels to generation would leak the rubric and invalidate comparison. A structurally matching scripted response is only a harness self-check. Other-actor source material can be cited to explain a boundary, but it cannot become a reason, non-final preference, or update attributed to the queried actor. The scorer checks ID scope, not whether prose truly refers to that actor. Callback errors count as `unknown`; missing responses count as `incomplete`. This small harness does not enforce external model timeouts or prove a provider honored any declared budget.

No core, MCP, hosted protocol, storage, credentials, live provider calls, or production data changes are in scope. If an appropriate implementation API is unavailable, this PR remains contract/scorer only, with no product improvement claim.

## Provisional integration checkpoint

Before choosing a product change, inspect actual ordinary-capture output and existing read surfaces on these cases. The local core already has source-addressed `reviewDecisionBasis` role/link constraints and a bounded `read_memory_sources` snapshot; these are reusable evidence surfaces, not an absent API. The basis decision role is currently adopted-only, so tentative state needs an explicit representation path. A candidate smallest next experiment is read-time, source-first decision-context reconstruction from an old memory hint, using existing receipts, links and supersession history. Missing links must be reported as incomplete rather than promising traversal. Test ordinary capture discovery as well as hand-wired link traversal. This is a candidate experiment pending contract results, not a durable graph architecture decision or authorization for new storage/API fields.

## Next actual-core/MCP experiment (not run here)

Use a small pre-registered set of held-out timelines and a fresh synthetic namespace per case. Ingest the same attributed events through the actual supported capture path. Query the same fixed answer model and prompt under three independently configured evidence arms: (1) current MOC recall, (2) opt-in linked decision context, and (3) bounded complete source snapshot. Keep question, model, output cap, sampling settings, event ordering, and capture provenance fixed. Do not pass the rubric to any generation stage. If a surface cannot expose one arm without new product work, mark that arm unavailable rather than approximating it silently.

Record per case/arm: required source evidence recall and irrelevant-source inclusion, adopted/tentative/needs-reconfirmation state and actor-scope accuracy under independent review, explicit-update direction and false links, wall latency by ingestion/retrieval/answer stage, input/output tokens and full incurred cost by stage. Preserve every failure, timeout, absent receipt, incomplete capture, and judge-unknown as denominators with separate counts; do not turn unknown into success or discard failed trials. Report scorer diagnostics and independent semantic judgments separately. The source-snapshot arm may reveal more personal text, so use only synthetic bounded data with explicit local opt-in and avoid treating larger context as intrinsically better.
