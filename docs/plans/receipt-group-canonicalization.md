The algorithm goal is useful source-backed recall without a redundant exact
membership serialization barrier. A focus receipt is the model-designated
terminal, an unverified organizational endpoint. Repeated membership adds no
evidence weight. A source passage may have multiple interpretive roles; neither
the raw annotation nor its canonical form proves a relationship, prerequisite,
adoption, currentness or truth. The raw-to-canonical transformation is not lossless.

## Acceptance and boundaries

- C1: use genuinely owned existing receipt-group preparation, compilation,
  authoritative assembly and flat answer packing. Private WeakMaps retain inner
  capabilities. Cloned data and hashes provide no authority. One new fixed
  factory shares the existing HTTP implementation and does not expose policy ports.
- C2: validate every raw occurrence before reducing any group: literal plain
  objects and dense arrays, exact fields and supplied IDs, native signal,
  immutable snapshots, identity/scope/revision, at most six raw groups and five
  raw context entries plus terminal, three distinct cards/group and input.limit
  cards in the raw union. Unknowns and malformed values are never dropped.
  Existing request/HTTP 6000-token, raw output/refs 1024-token, output 40000-character,
  snapshot and response-byte bounds remain. Duplicate JSON keys fail in the
  existing transport parser before compilation.
- C3: independently per group, keep first occurrence of each exact context ID,
  then remove the unchanged terminal ID from context. Preserve every group,
  group order and cross-group sharing. Endpoint order is surviving contexts
  followed by terminal. Card order is first card occurrence in this canonical
  sequence, which can differ from raw encounter order. No semantic/date sort,
  ID rewriting, group merging, relationship inference or extra generation.
  Every v1-accepted proposal remains identical; canonicalization is idempotent.
  Empty groups still abstain.
- C4: compiled.proposal is the immutable original raw proposal returned by
  transport. canonicalProposal is separate, with separate SHA256 and fixed
  policy/version/removal counts. Actual successor request/proposal identities,
  derived v1 request/proposal identities and derived CP request/proposal identities
  remain distinct. First literal provider response/body/hash/usage remain existing
  transport evidence. Flat answers contain complete authoritative source roles

- C5: one invocation/generation/take, exhausted failures and assembly, no retry
