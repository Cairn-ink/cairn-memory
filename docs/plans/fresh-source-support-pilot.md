# Fresh source-support capture/recall pilot (S6e)

Private dependent continuation after S6d exact-head dual review. No public
delivery, publication, deployment or production data. Implementation and offline
verification precede any paid execution.

## Purpose and evidence boundaries

Eight independently authored synthetic cases, subsequently seen by the root,
are new sources, not blinded cases or retries of old failures. Freeze exact
messages, one natural query per case and evaluator-only rubric before any
paid request. Never pass rubric/expected answers to extraction, qualification,
selection or ranking. No answer-generation/judge calls and no general accuracy
or comparison claim. Retain every failed, empty and not-run denominator slot.

## Acceptance

- E1: New fixed source-support fixture and operator with a separate immutable
  ledger-scoped source-support-v1 intent. Freeze fixture hash, source helper
  pins, installed archive and source correspondence before sending. Reject
  replay/occupied partial intent, altered sources, unknown options and artifact
  drift without requests. Never modify old fixtures, outcomes or entrypoints.
- E2: Add only closed source-support session and attempt factories reusing
  existing candidate guard/accounting. Allow baseline extract, qualifyCandidates,
  classify, select and rank on count/generation endpoints. No configurable
  methods/caps, v1 qualification, reconcile, host answer or judge. All old
  factories retain their original limits and method denials.
- E3: Reuse existing candidate-qualification-heldout-v1 capability exactly.
  Require its existing valid immutable binding; do not provision or rename it.
  Verify old capability bytes unchanged. Share the existing phase ledger,
  policy and checkpoint; no new total budget, refunds or failed-case retries.
- E4: Fixed maximum 96 HTTP requests / 480000 microUSD reservation at 5000
  per count or generation HTTP, within original US$50. Require settled exact
  checkpoint and sufficient conservative headroom. Serialize requests, persist
  before send, recheck pins/accounting, and permanently halt on drift, unknown
  settlement, persistence failure, transport failure, cap or read-only violation.
- E5: Each of eight cases gets a fresh DB/namespace and one actual installed
  v2 MCP capture. Inspect admitted sources, then exactly one fixed qualified
  recall on successful nonempty capture. Maximum six capture HTTP and six recall
  HTTP per case; no phase can borrow another phase's cap. Keep complete source
  qualifiers in existing counted budgets; no fallback or trimming to force recall.
- E6: Close and reopen successful captures, inspect exact source-qualified
  records and replay original capture only under zero-request fence. IDs,
  qualifications and sources must match. Never recapture failed events.
  Preserve separate capture, recall, cold evidence and overall statuses.
- E7: Bound and privately persist synthetic raw requests/responses, diagnostics,
  fixture/provenance, per-case evidence and budget-before/after. Parent alone
  holds real key; child receives proxy token only. Redact key from persisted
  evidence and finite failures. No source/model output in ordinary CLI errors.
- E8: Independent tests verify method isolation, exact caps, missing/wrong
  capability cannot create a grant, concurrent/drift/pin/persistence/readonly
  failure and occupied intent. Root actual installed fake-provider cases cover
  success, capture failure, recall failure, upstream halt and reentry zero HTTP,
  plus final-byte correspondence and key absence. Both Node22.16 and24 full
  required gates and independent exact-head Standards/Spec must pass first.
- E9: Only after gates, execute once with original private phase ledger and
  read-only authorized local key. Re-read aggregate immediately before run.
  Preserve original eight-case denominator, failures and unknown costs.
  Independently judge source sufficiency, descriptor usefulness/accuracy,
  attribution/commitment/conditions, unsupported strengthening and recall
  availability against frozen rubric. Storage success is not semantic pass.
