## Acceptance

- RC1: Freeze three new synthetic histories and a separate rubric: explicit
  retraction of a mistaken report; genuine verified premise failure that must
  remain visible; both together, with two reasons in distinct premise memories.
  Use at most six memory refs per case. Record event dates in the original
  source text, with arrival order explicit. Do not mistake a later import for
  a later event, a proposal for adoption, or a correction for a world change.
  Each decision retains its recorded choice; no permission to act is implied.
- RC2: Input and oracle are separate files. Provider-facing input is ONLY the
  canonical source receipts already accepted by the existing core. Expected
  links, scenario labels, seed graphs, rubric and expected statuses never enter
  model payload. Seed proposals are explicitly scripted, not measured model
  errors. Scope is relation judgment on supplied sources, not extraction,
  retrieval, natural host selection or automatic correction discovery.
- RC3: A bounded diagnostic runner uses the real public core with injected
  model ports and caller-provided fresh synthetic database. Manually admit the
  sources, seed known proposals using the default append-only API, invoke
  `reviewRationale` once with replacement and all current refs, then retain
  before/after source records, review result and every incident graph. Never
  patch SQL or manufacture successful model responses in the runner. No retry.
  Capture/review failure must remain a failed record, not an empty proposal.
- RC4: Fresh keyless child-process inspection must match warm persisted source
  and graph views. Assert exact graph tuples using receipt identities and
  all incident views, not only default reachable context. Sources and revisions
  remain unchanged. A challenge withdrawal is unassessed, not confirmed;
  preserved genuine challenge still requires reconfirmation.
- RC5: Offline tests inject correct selective output, indiscriminate clearing,
  append-only preservation of the known mistake, provider failure and malformed
  output. Structural success and semantic rubric success are separate results:
  the clear-everything control must NOT pass the rubric, and failure must not
  look like successful correction. Rubric scoring must not drive production
  writes or retry. Freeze exact expected receipt-backed edges for the synthetic
  controls, with documentation of supported alternative-edge ambiguity for
  later human review; do not label every different real model tuple incorrect.
- RC6: Document a future once-only comparison ceiling of three reviews, six
  guarded HTTP attempts, no answer/judge calls and no retry. Before any paid run
  require an independently reviewed operator, immutable source/artifact/fixture/
  rubric pins, an exclusive new attempt, shared-ledger headroom and fake-HTTP
  rehearsal. This offline slice grants none of those capabilities. Model sees
  no old graph, so this tests fresh inference plus replacement, not awareness
  of a previous verdict. Even three passing cases justify only broader held-out
  evaluation, not a reliability score or changing product defaults.
- RC7: Run new and affected suites on Node22.16/24, generic/JSON/strict plugin
  gates and independent fixed-point Standards/Spec review. Preserve the single
  shared engine, current provider prompts, model defaults and existing guards.
